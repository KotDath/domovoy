# День 9: история с отдельным summary

Запуск Linux: `flutter run -d linux -t lib/day09_main.dart`. Для реального DeepSeek задайте `DEEPSEEK_API_KEY` в окружении процесса. Демо использует две отдельные сохраняемые сессии и одинаковые 14 запросов: контроль без сжатия и режим с summary. В обоих случаях модель — DeepSeek Flash, ответы и токены поступают через production AgentRuntime.

Для браузерной записи соберите отдельную точку входа и скопируйте завершённую сборку в стабильную папку перед другими Flutter web сборками:

```sh
flutter build web --release --no-web-resources-cdn --no-wasm-dry-run -t lib/day09_web_main.dart -o /tmp/domovoy-day09-web-build
python3 -c 'import shutil; shutil.copytree("/tmp/domovoy-day09-web-build", "/tmp/domovoy-day09-web-served", dirs_exist_ok=True, symlinks=False)'
python3 tool/live_proxy.py --directory /tmp/domovoy-day09-web-served --port 8767
```

Откройте `http://localhost:8767`. Ключ требуется только Python relay (`DEEPSEEK_API_KEY`); браузерная сборка содержит публичный маркер. В готовой папке проверьте `assets/FontManifest.json` и `assets/fonts/MaterialIcons-Regular.otf`.

Для видео нажмите «Следующий шаг» пять раз. На пятой законченной паре сообщений режим summary делает отдельный вызов модели, сохраняет структурированное резюме старой части и оставляет последние две пары без изменений. Раскройте блоки «Сохранённое summary» и «Последние сообщения без сжатия». На десятом шаге появляется второе summary; счётчик интервала продолжает отсчитывать исходные сообщения, хотя длина истории уменьшилась. Кнопка «Запустить все 14» проводит оставшиеся одинаковые запросы в обоих режимах. Можно запустить всё одной кнопкой из пустого состояния; кнопка «Новый сценарий» создаёт новую пару сессий.

На последнем шаге сравните реальные ответы и восемь проверочных фактов: «Север», действующий бюджет `150000`, 15 ноября, email, регион хранения, отсутствие онлайн-оплаты, 45 минут и правило отмены. Нажмите на заголовки шагов, чтобы показать одинаковые входные формулировки. Полностью перезапустите приложение или обновите браузерную страницу: прогресс, summary, хвост и расход должны восстановиться. Конкретный ответ модели может отличаться; пропуск или подмена факта видны в соседних ответах.

Если в браузере сохранился старый 12-шаговый сценарий, приложение попросит начать новый: оно сверяет исходные запросы в сохранённой контрольной истории с текущим порядком шагов и не продолжает несовместимую запись как будто это тот же сценарий.

Таблица берёт только физические вызовы API из ledger: отдельно обычные ответы, отдельные вызовы summary и их сумму. «Последний запрос» показывает API input последнего ответа в каждом режиме. Input уже включает cache read, output уже включает reasoning; эти компоненты не прибавляются повторно. Cache hit = cache read / input. Если API не сообщил метрику, показывается «—» или частичная сумма с `+`, а не оценка. Строка «Разница» — контрольный суммарный расход минус суммарный расход режима с summary, включая цену построения summary; положительное число означает меньший общий расход с summary. Сокращение последнего запроса не гарантирует меньший общий расход на 14 шагах.

Первый реальный прогон с общей инструкцией summary показал ограничение, которое важно назвать в записи: контроль потратил 18289 токенов и назвал 8/8 фактов; режим summary потратил 20731 токен с учётом двух созданий резюме и назвал 7/8, потеряв имя «Север». Последний API input при этом был меньше: 1928 против 2709. Поэтому инструкция Day 9 теперь просит компактно сохранять точные решения пользователя и поздние изменения. Числа следующего прогона следует показывать из живого API, не переносить из первого.

Промежуточная проверка короткой инструкции остановилась на десятом шаге: второе summary достигло лимита вывода 768 токенов, и JSON не был принят. Уже завершённые вызовы и их расход остались в ledger. Окончательный вариант передаёт модели краткие правила через system prompt, требует перенести действующие значения из предыдущего summary и оставляет безопасный предел 1536 токенов. Два целевых API-вызова на репрезентативной истории вернули корректный JSON; второе резюме сохранило восемь проверочных значений, доступных к шагу 8, за 445 output-токенов. Это проверка качества сжатия, а не замена полному сравнению на 12 шагах.

Третий реальный прогон старого 12-шагового сценария сохранил 8/8 фактов в обоих режимах. Контроль: 16921 input / 861 output / 17782 всего. Режим summary: 13760 / 1193 / 14953 для ответов и отдельно 3586 / 619 / 4205 для двух резюме, вместе 17346 / 1812 / 19158 — на 1376 токенов дороже контроля. Последний запрос был заметно короче: input 1263 против 2601. Два новых шага перед итоговым ТЗ проверяют приёмку уже согласованных требований, не вводя новых фактов; они дают ещё два последовательных запроса, чтобы увидеть, как меняется общий расход.

Итоговый реальный 14-шаговый прогон вернул все 8/8 контрольных фактов в обоих ответах. Без сжатия: 14 ответов, input 22906, output 1570, всего 24476, чтение кэша 19584. Со сжатием: 14 ответов 18080 / 1983 / 20063, отдельно два summary 3380 / 793 / 4173, вместе 16 физических вызовов 21460 / 2776 / 24236. На этом сценарии общий расход оказался меньше на 240 токенов (около 1%); последний ответ получил input 2710 вместо 3692 (на 26,6% меньше). После второго summary сохранены четыре последних исходных сообщения, счётчик обработанных исходных сообщений равен 20. Экономия небольшая и зависит от длины следующих запросов и цены самого summary; не переносите эти числа на другую модель или беседу.

После обновления страницы все 14 шагов, оба последних ответа, два поколения summary и приведённые выше API-суммы восстановились из сохранённого состояния.
