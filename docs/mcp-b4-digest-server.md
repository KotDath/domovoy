## Контракт фабрики для B9

```dart
final pins = DigestModelPinRegistry(
  // Ключ запуска приходит из доверенного контекста вызова, а не из аргументов.
  scopeKeyOf: (scope) => scope.meta['domovoy/runScope'] as String?,
);
final digest = DigestMcpServerFactory(
  registry: appRegistry,        // существующий реестр Domovoy
  pins: pins,
  limits: const DigestLimits(), // опционально
  clock: const SystemDigestClock(),
);
localHost.register(digest);
await localHost.start('digest');  // serverId стабилен: 'digest'

// Вокруг запуска чата/задачи:
pins.registerScope(runScopeKey, runModelRef);   // на старте запуска
pins.releaseScope(runScopeKey);                 // когда запуск завершился
// при остановке приложения:
pins.clear();
```

`serverId` — `digest`, версия `1.0.0`, displayName `Digest`. Фабрика не
создаёт ни HTTP-клиента, ни хранилища секретов: вызов идёт через тот же
`LlmProviderRegistry` и те же credentials, что и чат. `factory.synthesizer`
отдаётся для диагностики и композиционных тестов.

## Модель на один вызов: контракт и что осталось подключить

Требование «модель закреплена за запуском» реализовано узким контрактом
`DigestModelPinResolver.resolve(DigestInvocationScope)`: сервер вызывает
резолвер **один раз на `tools/call`**, до любого обращения к провайдеру, и
использует возвращённый `DigestModelPin` только для этого вызова. Резолвер
не кэшируется и не читает глобальную «текущую модель»: два параллельных
вызова с разными ключами запусков получают разные `ModelRef`
(регрессия: «two concurrent calls with different pins stay isolated»).
Если пин не найден, вызов честно падает с `[digest:model_unavailable]`, а не
берёт модель другого чата/задачи.

**Оставшееся подключение (B9 обязан явно закрыть).** Текущий мост B2 не
может передать доверенный выбор на сервер:

- `ToolInvocation` (`core/agents`) не несёт идентификатор запуска/сессии;
- `McpHost.callTool` и `McpSdkConnection.callTool` не отправляют request
  `_meta`;
- клиентская MCP-сессия локального сервера общая для всех чатов и задач,
  поэтому `extra.sessionId` не различает запуск.

Минимальный план для B9 (без ослабления прав):

1. Передавать из рантайма агента/задачи доверенный ключ запуска (например
   id агентской сессии или `runId`) в `tools/call` через `_meta` (поле
   `_meta` не доступно модели: оно часть конверта, а не аргументов).
2. Собирать `DigestModelPinRegistry` с `scopeKeyOf`, читающим этот ключ, и
   регистрировать `ModelRef` запуска на старте, снимать по завершении.
3. Не подставлять fallback-модель: пока ключ не проведён,
   `UnavailableDigestModelPinResolver` даёт видимую `model_unavailable` для
   каждого вызова.

**Условие интеграции для схемы с `_meta`.** Ключ запуска в `_meta` — это
полномочие, поэтому он допустим только для вызовов, которые Domovoy сам
отправляет своему локальному серверу:

- локальный MCP-endpoint доступен только клиентам Domovoy (loopback HTTP с
  короткоживущим bearer-токеном либо in-process stream); произвольному
  стороннему клиенту соединение и токен не выдаются;
- сервер по-прежнему не принимает `ModelRef` из `_meta`: клиент передаёт
  только ключ, а модель сервер берёт из собственного
  `DigestModelPinRegistry`, поэтому угаданный или продублированный ключ не
  даёт выбрать чужую модель иначе как для уже активного запуска;
- ключи запусков должны быть непредсказуемыми (случайный id, а не
  последовательный номер), не логироваться и не попадать в трассу; при
  остановке приложения `pins.clear()` снимает все пины.

Иначе клиент, угадавший ключ другого запуска, мог бы получить его модель:
без этих условий схему из пункта 1 подключать нельзя.

До этого шага инструмент `digest` присутствует в каталоге, но не может
успешно выполнить ни одну сводку — это осознанное fail-closed поведение.

## Инструмент и провод

| Tool | Вход | Результат |
|---|---|---|
| `summarize_papers` | `topic` (обязательный), `papers` — 1–10 полных Paper v1 (как их отдаёт `arxiv.search_papers`), `language`?, `goal`? | `structuredContent` — Digest v1 (`sourceScope: abstract`) + короткий текст |

- Схема входа и выхода строго типизирована, `additionalProperties: false` у
  всех объектов; обе схемы проходят профили B2
  (`openaiChatCompletions`, `openaiResponses`, `portable`) и проверяются
  валидатором B2 на реальном результате. Объявленный `outputSchema` требует
  `structuredContent` на успехе — сервер его всегда возвращает.
- Каждый пункт `Digest.items` привязан к переданному arXiv ID; ссылка
  `abstractUrl` строится из проверенного ID. ID вне входа, дубликат или
  пропуск статьи — ошибка `model_response`, сводка не создаётся.
- `structuredContent` — ровно Digest v1 из `core/research`; текст явно
  сообщает, что просмотрены только аннотации, и называет модель.
- Одна и та же работа, переданная дважды (включая разные версии одного
  базового ID), отклоняется как `invalid_input`: у неё должен быть ровно
  один пункт сводки.
- Сервер не обращаетcя к arXiv и не пишет библиотеку: ни HTTP-клиента, ни
  файловых операций, ни второго хранилища ключей (проверяется статическим
  тестом по исходникам сервера).

## Проверка текста модели: структура против фактов

- **Структурная проверка ссылок.** Свободный текст модели (`overview`,
  `finding`, `limitation`) проверяется на явные ссылки на arXiv:
  `arXiv:<id>`, `arxiv.org/abs/<id>` и «голый» современный ID с
  границами (реальный месяц `YYMM`, не внутри более длинного числа).
  Ссылка вне переданного набора — `model_response`; некорректная ссылка
  после `arXiv:` — тоже `model_response`, причём в тексте ошибки остаётся
  только нормализованный ID, а не весь ответ модели. Ссылки на переданные
  работы разрешены, в том числе с версией. Это доказывает лишь то, что
  Digest не цитирует чужие идентификаторы, — не то, что утверждение
  действительно следует из аннотации.
- **Граница источника.** `Digest.items[].limitation` всегда начинается с
  серверной пометки `digestAbstractOnlyLimitation`
  (sourceScope=abstract) целиком: `DigestLimits.validate` запрещает
  `maxLimitationCharacters` короче самой пометки, поэтому усечённый
  дисклеймер невозможен. Допустимое ограничение модели (если оно помещается
  в остаток лимита) добавляется после пометки, а поля `overview`/текстовый
  результат всегда явно говорят, что прочитаны только аннотации. Так модель
  не может подменить проверенную границу источника.
- **Заявления о полном тексте.** Явные положительные утверждения вида
  «Полный PDF изучен» или «The full text was reviewed» отвергаются с
  `model_response` во **всех** принимаемых текстовых полях модели
  (`overview`, `finding`, `limitation`), а не только в `limitation`: любое
  из них иначе противоречило бы границе источника успешной сводки.
  Правдивые отрицательные оговорки («The full text was not reviewed»,
  «полный текст не изучен») принимаются: рядом с совпадением проверяется
  ограниченное окно отрицаний (`not`/`never`/`without`/`no`, `не`/`ни`/`без`/
  `никогда`; `not only`/`не только` отрицанием не считается), причём окно
  ограничено ближайшими разделителями предложений `[.;!?\n]` **с обеих
  сторон**, поэтому отрицание из соседнего предложения не может замаскировать
  положительное заявление. Границы отрицаний заданы явными классами, потому
  что `\b`/`\w` в Dart работают только с ASCII. Неоднозначные формулировки не
  угадываются — их перекрывает серверная пометка.
- **Что не проверяется.** Соответствие естественно-языковых утверждений
  (`finding`) содержанию аннотации недоказуемо без второго источника или
  независимой проверки; такие утверждения остаются данными модели и не
  помечаются как проверенные. Структурная валидация гарантирует только
  привязку ID/URL и заявление области источника.

## Лимиты

| Измерение | Значение по умолчанию |
|---|---|
| Статей на вызов | 1–10 |
| Байт на аннотацию / суммарно | 16 КиБ / 64 КиБ |
| Байт промпта | 192 КиБ |
| Байт ответа модели | 64 КиБ (накопление по мере стрима) |
| Полей Digest (`overview`/`finding`/`limitation`) | 4000/4000/1000 символов |
| Минимум `maxLimitationCharacters` | длина серверной пометки abstract-only; меньше — ошибка конфигурации |
| Model turns | ровно 1 (цикла нет; tool calls модели отвергаются) |
| Выходных токенов / бюджет по usage | 4096 / 65536 токенов |
| Дедлайн вызова | 90 с |

Лимиты проверяются на входе (`invalid_input`), на стриме (`output_too_large`)
и по отчёту провайдера (`budget_exceeded`). Если провайдер не сообщает
usage, бюджет не выдумывается: размер ответа и дедлайн всё равно ограничены.
`DigestLimits.validate` отвергает конфигурации, в которых серверная пометка
границы источника не помещается в `limitation` (в том числе `max=1`), до
любой работы провайдера; схема вывода использует тот же лимит, поэтому
schema-ограничение и серверная пометка остаются согласованными.

## Ошибки: домен, модель и провайдер различимы

Все ожидаемые ошибки — `CallToolResult(isError: true)` с префиксом
`[digest:<kind>]`; `structuredContent` у ошибок нет, поэтому outputSchema B2
проверяет только успешные результаты. Успех возможен только после полной
серверной валидации вывода модели.

| kind | Значение |
|---|---|
| `invalid_input` | аргументы, Paper, лимиты, промпт |
| `model_unavailable` | нет доверенного пина или модели нет в каталоге |
| `provider` | ошибки/отказ/обрыв потока провайдера, `content_filter` |
| `model_response` | пустой, не-JSON, обрезанный, неполный или не привязанный к входу ответ |
| `output_too_large` | ответ модели превысил байтовый лимит |
| `budget_exceeded` | usage провайдера превысил бюджет |
| `timeout` | истёк дедлайн одного model turn |
| `cancelled` | MCP-клиент отменил вызов |
| `internal` | непредвиденная ошибка сервера |

## Защита

- Аннотации и вывод модели — данные: промпт явно запрещает исполнять
  инструкции из аннотаций и вызывать инструменты, а весь ввод передаётся
  JSON-кодированием.
- Валидация вывода только на сервере: `Digest` строится из проверенных
  полей, неизвестные ID и лишние/пропущенные статьи отвергаются; свободный
  текст не может сослаться на работу вне входа (см. «Проверка текста
  модели»).
- Граница источника (`limitation` с пометкой abstract-only) всегда
  серверная: модель может добавить ограничение, но не заменить пометку и не
  заявить проверку полного текста.
- Глубина JSON в ответе модели ограничена (64 уровня) до `jsonDecode`, чтобы
  враждебный ответ не переполнил стек; текст ошибок и полей санитизируется и
  ограничивается по длине.
- Модель выбирается не моделью и не аргументами инструмента: только
  доверенным пином композиции.

## Ограничения и заметки

- **`Stream.timeout` не годится для дедлайна провайдера.** На `async*`-потоке,
  который ещё не выдал ни одного события, таймер `timeout` не срабатывает;
  «молчащая» модель повесила бы вызов. `DigestSynthesizer` использует явный
  `Timer`, отменяющий подписку и токен провайдера (регрессия: «times out when
  the model never answers»).
- MCP-слой `mcp_dart` сам валидирует `inputSchema` до обработчика: неполный
  Paper или лишний аргумент получают SDK-ошибку `isError` ещё до digest-кода.
  Собственная проверка сервера сохранена как defense in depth и покрыта
  тестом с невалидным `publishedAt`, который схема пропускает.
- Модели с обязательным reasoning (`kimi-k3`) получают
  `reasoningMode: enabled`, остальные — `disabled`: лишние рассуждения не
  тратят бюджет, а несовместимая комбинация не отвергается.
- Провайдеры, не отдающие usage, не дают проверить бюджет `maxTotalTokens`;
  ограничение опирается на `maxOutputTokens`, байтовый лимит и дедлайн.
- Реальный сквозной вызов модели (живой ключ DeepSeek) в B4 не выполнялся:
  корректность синтеза проверена скриптованным провайдером реестра, живые
  прогоны — задача B9/демонстрации дня 19.
- Проверка ссылок структурная: она ловит явные `arXiv:<id>`, `arxiv.org/abs`
  и голые ID, но не «замаскированные» упоминания (например, «вторая работа
  из списка») и не проверяет, что `finding` действительно следует из
  аннотации. Это честно отражено в разделе «Проверка текста модели»; для
  фактологической проверки нужен отдельный источник или независимый проход.
- Заявления о полном тексте отвергаются консервативным списком RU/EN
  формулировок: неоднозначные фразы не отвергаются, но и не могут заменить
  серверную пометку abstract-only.
- Голый ID распознаётся только в современном формате `YYMM.NNNNN` с реальным
  месяцем и границами «не внутри более длинного числа»; legacy-ID голым
  текстом не распознаются (только `arXiv:`/`arxiv.org/abs`), что осознанно
  снижает ложные срабатывания.

## Правки после ревью раунда 1

- **Ссылки вне входа в свободном тексте.** `overview`, `finding` и
  `limitation` теперь проверяются на явные arXiv-ссылки (`arXiv:<id>`,
  `arxiv.org/abs/<id>`, голый современный ID `YYMM.NNNNN` с реальным месяцем
  и границами), а не только `items[].arxivId`. Чужая ссылка или
  некорректный ID после `arXiv:` дают `model_response`; текст ошибки
  содержит только нормализованный ID и не эхоит ответ модели; ссылки на
  переданные работы (включая версии) разрешены. Проза вида «arXiv: см.
  таблицу» без цифр не считается ссылкой. Регрессии: «rejects an outside
  arXiv reference in the overview text», «rejects an outside arxiv.org URL
  in a finding», «rejects a bare outside arXiv id in a finding», «rejects an
  outside arXiv reference in a limitation», «rejects a malformed arXiv
  reference without echoing it», «does not echo the model answer in a
  citation error», «accepts references to supplied papers in model text»,
  серверный «rejects a foreign arXiv citation in model text».
- **Граница abstract-only не перезаписывается моделью.** В
  `DigestItem.limitation` всегда первой идёт серверная пометка
  `digestAbstractOnlyLimitation`; допустимое ограничение модели
  добавляется после неё и обрезается по `maxLimitationCharacters`, поэтому
  `limitation: "Полный PDF изучен"` больше не может выдать непроверенную
  границу за проверенную. Явные RU/EN заявления о полном тексте отвергаются
  с `model_response`. Регрессии: «rejects a model limitation that claims
  full-text review», «rejects an English full-text claim», «keeps the
  abstract boundary next to a model caveat», «bounds the combined limitation
  to the field limit», серверный «structuredContent and text keep the
  abstract boundary with a caveat»; обновлён «produces a grounded
  abstract-scope digest in one provider turn».
- **Условие интеграции `_meta`.** В документе зафиксировано, что ключ запуска
  в `_meta` допустим только для Domovoy-owned локальных вызовов (loopback с
  короткоживущим токеном или in-process stream), сервер не принимает
  `ModelRef` из `_meta`, ключи должны быть непредсказуемыми и не попадать в
  логи: иначе клиент, угадавший ключ, получил бы модель чужого запуска.
- **Red-before.** 13 новых/обновлённых регрессионных тестов падают на
  базовом коммите `fa68b34` (проверено `git stash` только
  `digest_synthesizer.dart`) и проходят после правок.

## Правки после ревью раунда 2

- **Заявления о полном тексте проверяются во всех полях.** `overview` и
  `finding` теперь проходят ту же проверку положительных утверждений, что и
  `limitation`, поэтому «The full text was reviewed» в обзоре или «Полный PDF
  изучен» в выводе по статье больше не попадают в успешный Digest.
  Регрессии: «rejects a full-text claim in the overview» (synthesizer и
  серверный вариант), «rejects a full-text claim in a finding».
- **Отрицательные оговорки не отвергаются.** Вокруг совпадения проверяется
  ограниченное окно отрицаний (`not`/`never`/`without`/`no`, `не`/`ни`/`без`/
  `никогда`; `not only`/`не только` — не отрицание), причём окно не
  переходит границу предложения после совпадения, поэтому правдивые оговорки
  встречаются и в прямом, и в обратном порядке («The full text was not
  reviewed», «полный текст не изучен», «полный текст проверен не был»), а
  отрицание из следующего предложения не скрывает положительное заявление.
  Границы слов заданы явными классами: `\b`/`\w` в Dart — ASCII-only и не
  видят кириллицу. Регрессии: «accepts a truthfully negated caveat in a
  limitation» (падал на раунде 1), «accepts a negated full-text statement in
  a finding», «accepts a negated caveat whose negation follows the verb»,
  «a later sentence negation does not hide a claim».
- **Пометка границы источника не усекается.** `DigestLimits.validate`
  отвергает `maxLimitationCharacters` короче `digestAbstractOnlyLimitation`
  (включая `1`) с ошибкой конфигурации до обращения к провайдеру, а
  `_limitationWithAbstractNote` либо возвращает пометку целиком, либо
  добавляет моделью написанную оговорку в остаток лимита. Регрессии:
  «rejects a limitation limit that cannot hold the server note», «a tiny
  limitation limit cannot build a synthesizer», «accepts a limitation limit
  exactly the size of the server note», «a boundary-sized limit keeps the
  complete server note»; схема вывода использует тот же лимит.
- **Red-before.** 7 новых/обновлённых тестов падают на базовом коммите
  `f01922d` (проверено откатом только `digest_synthesizer.dart` /
  `digest_limits.dart` через `git stash`) и проходят после правок; ещё 4
  теста-ограничителя (приём отрицаний и граничный лимит) проходят и до, и
  после — они фиксируют допустимые границы политики.

## Правки после ревью раунда 3

- **Отрицание из предыдущего предложения больше не маскирует заявление.**
  `_negationWindow` ограничивал окно разделителем `[.;!?\n]` только после
  совпадения; 16-символьный префикс мог захватить `Not`/`Не` из предыдущего
  предложения, и положительное утверждение считалось отрицательной оговоркой.
  Теперь префикс обрезается по ближайшему разделителю и перед совпадением,
  поэтому `overview: "Not reviewed. Full text was reviewed."` и
  `finding: "Не читали. Полный текст проверен."` дают `model_response`.
  Регрессии: «a prior sentence negation does not hide an English claim»,
  «a prior sentence negation does not hide a Russian claim»; правдивые
  отрицательные оговорки внутри одного предложения из раунда 2 продолжают
  приниматься (уже существующие тесты).
- **Red-before.** Оба новых теста падают на базовом коммите `15cb292`
  (проверено откатом только `digest_synthesizer.dart` через `git stash`) и
  проходят после правки; полный набор digest-тестов — 86.
