## Контракт фабрики для B9

```dart
final pins = DigestModelPinRegistry(
  // Ключ запуска приходит из доверенного контекста вызова, а не из аргументов.
  scopeKeyOf: (scope) => scope.meta['domovoy/runScope'] as String?,
);
final digest = DigestMcpServerFactory(
  registry: appRegistry,        // существующий реестр Domovoy
  pins: pins,
  limits: const DigestLimits(), // опционально
  clock: const SystemDigestClock(),
);
localHost.register(digest);
await localHost.start('digest');  // serverId стабилен: 'digest'

// Вокруг запуска чата/задачи:
pins.registerScope(runScopeKey, runModelRef);   // на старте запуска
pins.releaseScope(runScopeKey);                 // когда запуск завершился
// при остановке приложения:
pins.clear();
```

`serverId` — `digest`, версия `1.0.0`, displayName `Digest`. Фабрика не
создаёт ни HTTP-клиента, ни хранилища секретов: вызов идёт через тот же
`LlmProviderRegistry` и те же credentials, что и чат. `factory.synthesizer`
отдаётся для диагностики и композиционных тестов.

## Модель на один вызов: контракт и что осталось подключить

Требование «модель закреплена за запуском» реализовано узким контрактом
`DigestModelPinResolver.resolve(DigestInvocationScope)`: сервер вызывает
резолвер **один раз на `tools/call`**, до любого обращения к провайдеру, и
использует возвращённый `DigestModelPin` только для этого вызова. Резолвер
не кэшируется и не читает глобальную «текущую модель»: два параллельных
вызова с разными ключами запусков получают разные `ModelRef`
(регрессия: «two concurrent calls with different pins stay isolated»).
Если пин не найден, вызов честно падает с `[digest:model_unavailable]`, а не
берёт модель другого чата/задачи.

**Оставшееся подключение (B9 обязан явно закрыть).** Текущий мост B2 не
может передать доверенный выбор на сервер:

- `ToolInvocation` (`core/agents`) не несёт идентификатор запуска/сессии;
- `McpHost.callTool` и `McpSdkConnection.callTool` не отправляют request
  `_meta`;
- клиентская MCP-сессия локального сервера общая для всех чатов и задач,
  поэтому `extra.sessionId` не различает запуск.

Минимальный план для B9 (без ослабления прав):

1. Передавать из рантайма агента/задачи доверенный ключ запуска (например
   id агентской сессии или `runId`) в `tools/call` через `_meta` (поле
   `_meta` не доступно модели: оно часть конверта, а не аргументов).
2. Собирать `DigestModelPinRegistry` с `scopeKeyOf`, читающим этот ключ, и
   регистрировать `ModelRef` запуска на старте, снимать по завершении.
3. Не подставлять fallback-модель: пока ключ не проведён,
   `UnavailableDigestModelPinResolver` даёт видимую `model_unavailable` для
   каждого вызова.

До этого шага инструмент `digest` присутствует в каталоге, но не может
успешно выполнить ни одну сводку — это осознанное fail-closed поведение.

## Инструмент и провод

| Tool | Вход | Результат |
|---|---|---|
| `summarize_papers` | `topic` (обязательный), `papers` — 1–10 полных Paper v1 (как их отдаёт `arxiv.search_papers`), `language`?, `goal`? | `structuredContent` — Digest v1 (`sourceScope: abstract`) + короткий текст |

- Схема входа и выхода строго типизирована, `additionalProperties: false` у
  всех объектов; обе схемы проходят профили B2
  (`openaiChatCompletions`, `openaiResponses`, `portable`) и проверяются
  валидатором B2 на реальном результате. Объявленный `outputSchema` требует
  `structuredContent` на успехе — сервер его всегда возвращает.
- Каждый пункт `Digest.items` привязан к переданному arXiv ID; ссылка
  `abstractUrl` строится из проверенного ID. ID вне входа, дубликат или
  пропуск статьи — ошибка `model_response`, сводка не создаётся.
- `structuredContent` — ровно Digest v1 из `core/research`; текст явно
  сообщает, что просмотрены только аннотации, и называет модель.
- Сервер не обращаетcя к arXiv и не пишет библиотеку: ни HTTP-клиента, ни
  файловых операций, ни второго хранилища ключей (проверяется статическим
  тестом по исходникам сервера).

## Лимиты

| Измерение | Значение по умолчанию |
|---|---|
| Статей на вызов | 1–10 |
| Байт на аннотацию / суммарно | 16 КиБ / 64 КиБ |
| Байт промпта | 192 КиБ |
| Байт ответа модели | 64 КиБ (накопление по мере стрима) |
| Полей Digest (`overview`/`finding`/`limitation`) | 4000/4000/1000 символов |
| Model turns | ровно 1 (цикла нет; tool calls модели отвергаются) |
| Выходных токенов / бюджет по usage | 4096 / 65536 токенов |
| Дедлайн вызова | 90 с |

Лимиты проверяются на входе (`invalid_input`), на стриме (`output_too_large`)
и по отчёту провайдера (`budget_exceeded`). Если провайдер не сообщает
usage, бюджет не выдумывается: размер ответа и дедлайн всё равно ограничены.

## Ошибки: домен, модель и провайдер различимы

Все ожидаемые ошибки — `CallToolResult(isError: true)` с префиксом
`[digest:<kind>]`; `structuredContent` у ошибок нет, поэтому outputSchema B2
проверяет только успешные результаты. Успех возможен только после полной
серверной валидации вывода модели.

| kind | Значение |
|---|---|
| `invalid_input` | аргументы, Paper, лимиты, промпт |
| `model_unavailable` | нет доверенного пина или модели нет в каталоге |
| `provider` | ошибки/отказ/обрыв потока провайдера, `content_filter` |
| `model_response` | пустой, не-JSON, обрезанный, неполный или не привязанный к входу ответ |
| `output_too_large` | ответ модели превысил байтовый лимит |
| `budget_exceeded` | usage провайдера превысил бюджет |
| `timeout` | истёк дедлайн одного model turn |
| `cancelled` | MCP-клиент отменил вызов |
| `internal` | непредвиденная ошибка сервера |

## Защита

- Аннотации и вывод модели — данные: промпт явно запрещает исполнять
  инструкции из аннотаций и вызывать инструменты, а весь ввод передаётся
  JSON-кодированием.
- Валидация вывода только на сервере: `Digest` строится из проверенных
  полей, неизвестные ID и лишние/пропущенные статьи отвергаются.
- Глубина JSON в ответе модели ограничена (64 уровня) до `jsonDecode`, чтобы
  враждебный ответ не переполнил стек; текст ошибок и полей санитизируется и
  ограничивается по длине.
- Модель выбирается не моделью и не аргументами инструмента: только
  доверенным пином композиции.

## Ограничения и заметки

- **`Stream.timeout` не годится для дедлайна провайдера.** На `async*`-потоке,
  который ещё не выдал ни одного события, таймер `timeout` не срабатывает;
  «молчащая» модель повесила бы вызов. `DigestSynthesizer` использует явный
  `Timer`, отменяющий подписку и токен провайдера (регрессия: «times out when
  the model never answers»).
- MCP-слой `mcp_dart` сам валидирует `inputSchema` до обработчика: неполный
  Paper или лишний аргумент получают SDK-ошибку `isError` ещё до digest-кода.
  Собственная проверка сервера сохранена как defense in depth и покрыта
  тестом с невалидным `publishedAt`, который схема пропускает.
- Модели с обязательным reasoning (`kimi-k3`) получают
  `reasoningMode: enabled`, остальные — `disabled`: лишние рассуждения не
  тратят бюджет, а несовместимая комбинация не отвергается.
- Провайдеры, не отдающие usage, не дают проверить бюджет `maxTotalTokens`;
  ограничение опирается на `maxOutputTokens`, байтовый лимит и дедлайн.
- Реальный сквозной вызов модели (живой ключ DeepSeek) в B4 не выполнялся:
  корректность синтеза проверена скриптованным провайдером реестра, живые
  прогоны — задача B9/демонстрации дня 19.
