## Original assignments

### Day 13. Task State Machine

Implement task state as a finite-state machine:

- task stage;
- current step;
- expected action;
- example: `planning → execution → validation → done`.

Verify pausing at any stage and resuming without explaining the task again.
Result: an agent with formalized task state. Format: video plus code/text.

### Day 14. State invariants and constraints

Add invariants that the assistant may not violate. Examples include the chosen
architecture, accepted technical decisions, stack constraints, and business
rules.

- Store invariants separately from the conversation.
- Explicitly include them in planner, worker, and verifier context.
- Refuse proposals that violate an invariant.
- Demonstrate a conflicting request and the refusal explanation.

Result: an assistant operating within declared invariants. Format: video plus
code/text.

### Day 15. Controlled state transitions

Define allowed states and transitions. The assistant may not skip a stage: it
cannot execute before plan approval and cannot finish before validation.
Demonstrate invalid transitions, the assistant response, and correct continuation
after a pause.

Result: an assistant with a controlled task lifecycle. Format: video plus
code/text.

## Product contract

The user enters `/plan`; the next message becomes the goal. A planner produces a
directed acyclic plan of at most six nodes. The user may revise the draft and is
the only actor allowed to approve it.

After approval the workflow is automatic:

`node → fresh verifier → next ready node → final composition → final verifier`

There are no per-node confirmation gates. Human input is needed only for pause,
resume, replan, cancel, an exhausted repair attempt, or a blocking error.

The global phases are `planning`, `execution`, `validation`, and terminal
`done`. Execution nodes use `pending`, `ready`, `running`, `verifying`,
`repairing`, `succeeded`, `failed`, and `interrupted` statuses. A pure reducer
and transition guards are the only authority that may change task state.

One active task is allowed per chat session. Replanning invalidates all previous
node and final results and requires approval again. Pausing preserves the phase
and checkpoint. A result arriving from an interrupted or stale revision is not
committed. On application restart, an in-flight node becomes `interrupted` and
the task resumes only after an explicit resume.

The version-1 gateway is single-flight. Switching to another chat therefore
pauses the previous chat's active task and persists its checkpoint; returning to
that chat requires an explicit resume. Replanning is not offered while paused.

Task snapshots and project/task invariant policies use separate versioned JSONL
streams. Revision compare-and-swap and the one-active-task guard are enforced by
one application-scoped repository instance; independent concurrent writers are
not supported. Startup uses the explicit recovery operation, while ordinary
reads never interrupt a live invocation. A torn final line is ignored, complete
corruption fails closed for its owning chat, and unrelated chats remain usable.
If corruption destroys the first complete record so that the owner cannot be
identified safely, task-catalog operations fail closed instead of assuming that
the stream belongs to another chat. Streams are bounded to 8 MiB in version 1.

## Guards and errors

- Execution requires an approved plan.
- A node requires all dependencies to have succeeded.
- Validation requires every node to have succeeded.
- Done requires successful final-validation evidence.
- A paused task cannot advance.
- Expected revision must equal the stored revision.
- A deterministic invariant failure prevents an LLM call.

Failures expose stable codes: `PLAN_APPROVAL_REQUIRED`, `INVALID_TRANSITION`,
`VALIDATION_REQUIRED`, `INVARIANT_VIOLATION`, `TASK_PAUSED`,
`REVISION_CONFLICT`, `REPLAN_REQUIRED`, and `REPAIR_EXHAUSTED`.

## Invariants

Project and task invariant records live outside chat history. A record has an ID,
scope, category, description, checker type, checker parameters, active flag, and
revision. Version 1 supports required terms, forbidden terms, maximum characters,
and semantic review. Deterministic rules run first. Prompts include the applicable
rules, but Domovoy records only rule IDs and concise explanations, never hidden
chain-of-thought. Version 1 exposes the task-scope editor in the task card;
project-scope policies are supported by the repository and application API but
their project-settings editor is deferred.

## Agent isolation

Planner, node workers, node verifiers, final composer, and final verifier are
fresh bounded invocations. They receive the goal, approved plan, applicable
invariants, current node, and dependency outputs only. They do not inherit the
chat transcript. One repair is permitted for a rejected node or final answer.
Version 1 produces Markdown and exposes no filesystem, shell, or mutating tools.

## Commands and UI

- `/plan` starts goal capture.
- `/task status`, `/task pause`, `/task resume`, `/task replan`, and
  `/task cancel` control the workflow.
- A task card above the chat shows phase, current node, expected action,
  progress, errors, valid actions, and the verified final result at `done`.
- The card edits task invariants and exposes diagnostic invalid-transition
  attempts for the Day 15 demonstration. Diagnostic actions never bypass guards.
  A rejected diagnostic remains visible across automatic revisions in the same
  phase, then clears on the next human action or phase change.

## Acceptance and video scripts

### Day 13

Start a plan of one to six nodes, approve it, observe automatic node advancement,
pause during execution, restart the app, resume without restating the goal, and
reach done automatically with the verified result visible.

### Day 14

Add a forbidden-term invariant, submit a conflicting plan revision, observe an
`INVARIANT_VIOLATION` with the rule ID, then submit an allowed revision and run it.

### Day 15

Before approval, use the diagnostic execution action and observe
`PLAN_APPROVAL_REQUIRED`. During execution, use the diagnostic done action and
observe `VALIDATION_REQUIRED`. Resume normal automatic routing and reach done
only after validation evidence exists.

Each scenario must pass on the Android emulator. Exact prompts, screenshots,
logs, and local MP4 paths (when screen recording is available) are recorded in
the [Android demo runbook](day-13-15-video.md). Concrete QA artifacts are
recorded here after the independent device run. Secrets are entered off-camera
and stored only through `flutter_secure_storage`.
