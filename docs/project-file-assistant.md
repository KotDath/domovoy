# Локальные файловые задачи

Выберите проект, откройте его чат и отправьте `/files` с целью, например:
«Проследи, как публичный API передаёт данные между компонентами. Сверь документацию
с реализацией, исправь неточности и сохрани новую краткую архитектурную заметку».
Ассистент сам выбирает файлы и порядок поиска, чтения и изменений. Запрос
разрешает нужные для этой цели локальные изменения без подтверждения каждого файла.
Файлы сохраняются в выбранном корне проекта. Публикация, коммит и push не выполняются.

На Android сначала создайте пустой локальный проект. Откройте его «Базу знаний» →
«Импорт checkout .tar в пустой проект» и выберите несжатый USTAR `.tar`,
подготовленный общим экспортёром. На desktop выберите разрешённую локальную директорию.
[Импорт и индексация README/docs](developer-assistant.md) остаются общими с `/help`.
Готовый актуальный Structure-индекс README/docs используется как дополнительный
контекст. Если индекса нет, он устарел или сервис недоступен, `/files` продолжает
работать через свежий файловый поиск; отсутствующий RAG не выдаётся за доказательства.
Для этого режима не нужно включать MCP-серверы или выдавать дополнительные MCP-права.

Раскройте карточку инструмента, чтобы видеть аргументы, результат и ошибку.
После успешной записи отдельная строка показывает путь и статус «Создан»,
«Изменён» или «Без изменений». Раскройте её для точного текста **до / после**.
Это снимок конкретной операции, а не выдуманный моделью diff; последующий `read`
показывает текущее сохранённое содержимое. Несколько операций над одним файлом
сохраняют отдельные снимки. Они переживают перезапуск вместе с обычным JSONL
транскриптом. Итог модели следует сверять с карточками инструментов.

Остановка задачи не отменяет уже сохранённые файлы. Ошибка в следующем файле
также не откатывает предыдущие изменения. Проверяйте успешные операции даже при
неполном ответе или ошибке провайдера. У неуспешной операции нет записи об успешном
изменении. При создании вложенного файла после ошибки могут остаться пустые каталоги.

## Доступ и точная запись

`/files` предоставляет только `read`, `ls`, `find`, `grep`, `write`, `edit`.
Список проверяет runtime при каждой операции. История предыдущих ходов, персональная
память, shell и дополнительные MCP-инструменты в этот ход не попадают.
Обычный чат сохраняет прежние инструменты, включая поддерживаемый платформой `bash`.
`/help` сохраняет свой read-only контур; headless `review` и `exec --read-only`
по-прежнему допускают только разрешённый snapshot `read`, без новых поисковых прав.

Все пути относительны выбранному корню: абсолютные пути, `..`, неоднозначные
разделители, Windows device names, управляющие символы, завершающие точка/пробел
в именах и символические ссылки запрещены. Активность проекта и доступ к
его корню проверяются заново на вызове и непосредственно перед записью;
внешний корень должен иметь право readWrite. Дополнительные директории не становятся
корнями записи. Эти файловые операции ограничены корнем; обычный shell не является
OS-песочницей и не входит в `/files`.

`read` возвращает SHA-256 `revision` **полного** UTF-8 файла, даже при чтении
страницы. Для `write` существующего файла нужен `expectedRevision` из `read`
или точный полный `expectedContent`. Без этого перезапись отклоняется. Если
ожидаемый файл исчез, операция также завершается конфликтом. `edit` заменяет
уникальные точные `oldText`, проверяет непересечение замен и поддерживает
`expectedRevision`, чтобы отклонять устаревшее чтение. Без revision точные замены
применяются к текущему файлу, сохраняя остальные байты. BOM, CRLF и Unicode вне замены
не нормализуются.

Перед сохранением проверяются актуальные исходные байты и отмена. Записи приложения
последовательны; подготовленный временный файл заменяет целевой атомарным rename
в том же каталоге. Сохраняются обычные Unix permission bits, включая executable;
set-ID/sticky bits, владельцы, ACL и extended attributes не переносятся. Windows
использует штатное поведение rename/ACL каталога. Dart не предоставляет переносимый
filesystem compare-and-swap: это защита от обнаруженных конкурирующих изменений,
а не гарантия против враждебного процесса, меняющего пути одновременно на уровне OS.
При конфликте агент должен прочитать файл заново и пересмотреть изменение.

## Переносимый поиск и пределы

`ls`, `find`, `grep` реализованы на Dart IO, без git, rg, fd или shell. Названия
и базовые параметры знакомы по Pi. Это ограниченная переносимая реализация:
она не интерпретирует `.gitignore`, не скачивает утилиты, не поддерживает все
флаги Pi/rg/fd. PowerShell не добавлен.

| Инструмент | Параметры и результат |
| --- | --- |
| `ls` | `path` (по умолчанию `.`), `limit` (500), `offset` (0). Немедленные файлы/каталоги, сортировка по пути, тип и путь от корня проекта. |
| `find` | `pattern`, необязательные `path`, `limit` (100), `offset`. Рекурсивный поиск файлов. `*` и `?` не пересекают `/`, `**` пересекает; `**/` допускает ноль каталогов. Шаблон без `/` сопоставляется с basename на любой глубине; с `/` — с путём от `path`. Нет braces/classes/escape syntax, максимум 256 символов. |
| `grep` | `pattern`, `path`, `glob`, `literal`, `ignoreCase`, `context` (0–5), `limit` (100), `offset`. Совпавшие строки с путём от корня, номером от 1 и необязательным контекстом. Literal ищет подстроку. Regex — безопасное плоское подмножество, без групп и alternation; неподдерживаемый шаблон даёт ошибку с советом разделить поиск. |

Общий предел страницы — 500 результатов / 48 KiB сериализованных записей;
`offset` — 0–10000. `nextOffset` продолжает страницу результатов, `truncated`
предупреждает о неполноте. При пределе обхода сужайте `path`: offset не обходит
предел сканирования. Страницы пересчитываются по текущему дереву и не являются
замороженным snapshot при внешних изменениях.

Обход ограничен 10000 просмотренных записей, 10000 детьми одного каталога,
32 уровнями и 16 MiB суммарного чтения для grep. Поиск пропускает binary,
невалидный UTF-8 и файлы больше 1 MiB с явными `skipped`/`warnings`.
Строки grep ограничены 1000 символами; для полного текста используйте `read`.
`read` читает UTF-8 файл до 1 MiB и возвращает до 2000 строк / 50 KiB за вызов
(настраиваются offset/limit). Изменение ограничено 128 KiB до и после на файл;
снимок обеих версий входит в JSONL и контекст модели без сокращения. JSON escaping
может увеличивать размер; общие пределы runtime/JSONL не снимаются.

Фиксированно исключаются `.git`, каталоги кэшей/сборок/виртуальных окружений и конкретные
credential stores: `.env`, `.env.*`, `.ssh`, `.aws`, `.azure`, `.kube`, `.docker`,
`.config/gh`, `.config/gcloud`, `.config/hub`, `.gem/credentials`, `.bundle/config`,
известные key/credential filenames и расширения `.pem/.key/.keystore/.jks`.
Обычные `credentials.dart`, `secret-management.md` и source-файлы вроде `scripts/build` доступны;
имена кэшей исключаются как каталоги, а не как обычные файлы.
Это не детектор любых секретов внутри произвольного исходника.

## Воспроизводимые демонстрации в изолированных копиях

Используйте две отдельные копии реальных исходников: Domovoy и encode/httpcore.
Зафиксируйте upstream SHA, ветку, лицензию и SHA-256 архива до импорта. Для
Domovoy используйте принятый кандидат, для HTTPcore — выбранный upstream commit
(BSD-3-Clause). Не работайте в исходном checkout и не отправляйте изменения upstream.
Для импорта с Git-контекстом нужна самостоятельная копия `.git`, не linked-worktree
с абсолютным gitdir. Подготовка несжатого USTAR `.tar` через `tool/export_project.py`, ограничения
архива и настройки модели описаны в [общей инструкции](developer-assistant.md).

Два примера целей (без заданного списка файлов или порядка инструментов):

- Domovoy: «Изучи, как проект разрешает локальные инструменты и исполняет их
  вызовы. Улучши документацию для новых сопровождающих: она должна соответствовать
  реализации, объяснять read-only режимы и просмотр результатов. Сохрани улучшения
  существующей документации и новую краткую архитектурную заметку. Покажи реальные
  изменения. Ответь по-русски».
- HTTPcore: «Проследи поведение повторных соединений от пула до синхронной и
  асинхронной реализаций. Улучши документацию, чтобы сопровождающий понимал,
  какие ошибки повторяются, какие передаются вызывающему коду и как реализации
  остаются согласованными. Обнови подходящую существующую документацию и создай
  краткую справочную заметку. Сохрани и покажи изменения. Ответь по-русски».

В UI добавьте `/files` перед целью. В каждом запуске наблюдайте самостоятельный
поиск и чтение как минимум трёх релевантных файлов, анализ, изменение существующего
документа и создание нового, карточки before/after и повторное чтение с диска.
Не считайте финальное обещание модели доказательством записи.

Для локальной проверки того же production runtime, UI preparer и реального RAG
без Flutter engine существует пробник:

```sh
dart run tool/project_files_smoke.dart /absolute/disposable-checkout \
  /absolute/goal.txt /absolute/external-artifacts http://127.0.0.1:8765
```

Он использует имеющийся `DEEPSEEK_API_KEY`, не печатает ключ, не запускает сервисы
и не меняет настройки. Он строит настоящий Structure-индекс README/docs через
указанный gateway, передаёт цель обычному агенту и сохраняет `progress.jsonl`,
`report.json`, `answer.md` и сессию JSONL вне корня проекта. Отчёт содержит реальные
аргументы/результаты, RAG revisions, before/after и свежее чтение сохранённых файлов;
reasoning и сырые запросы не экспортируются. Это платный реальный вызов провайдера,
не замена Android-проверки. Проверяйте terminal и число фактических чтений/изменений.
Для сброса создайте новую копию того же исходного SHA и повторно импортируйте её;
не выполняйте destructive reset в пользовательском проекте.
