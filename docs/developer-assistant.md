# Помощник по локальному проекту

`/help <вопрос>` использует текущие README/docs выбранного проекта, векторный
поиск M1, начальные фрагменты корневого README и встроенный MCP-инструмент `mcp_project__git_branch`. Без вопроса
`/help` запрашивает назначение, структуру и основные компоненты проекта.
Ответ генерирует настроенная модель; готовых ответов для отдельных репозиториев нет.

## Подготовка checkout

На desktop создайте проект через «Прикрепить существующую папку» и выберите
локальный checkout. Чтение проверяет актуальность предоставленного доступа.
Git CLI для чтения ветки в приложении не нужен.

На Android создайте новый пустой проект. На компьютере подготовьте архив:

```sh
python3 tool/export_project.py /absolute/path/to/checkout /tmp/project.tar
# Публичный URL и выбранная ветка/тег также поддерживаются:
python3 tool/export_project.py https://example.org/owner/repo.git /tmp/project.tar --ref branch-name
```

Нужны Python 3 и Git. Экспортёр делает свежий самостоятельный shallow clone
выбранного HEAD/ветки/тега, включая настоящие `.git/objects`, HEAD и refs.
Локальные незакоммиченные изменения не экспортируются. Нельзя передавать URL
с логином, паролем, query или fragment. GitHub source ZIP не содержит `.git`
и для этого импорта не подходит. Связанный worktree экспортируется через clone,
его абсолютные `gitdir`-указатели не переносятся.

`PROJECT_PROVENANCE.json` внутри архива и соседний `project.provenance.json`
содержат исходный URL/путь, commit, branch, найденные файлы лицензии и baseline.
Перед публикацией экспорт проверяет пути во всех commit, попавших в shallow clone.
Если tracked-путь соответствует `.env*`, `.pem`, `.key`, `.jks`, `.keystore`,
`id_rsa`, `id_ed25519`, `credentials.json` или `service-account.json`, экспорт
**отказывает**, не создаёт новый архив и не заменяет существующий. Это касается
также консервативно совпадающих template/fixture-путей: исключить только рабочий
файл недостаточно, его blob остался бы в Git. Значения файлов не печатаются.
Обычные credentials.dart и docs/credentials.md сохраняются.
Фильтры зависимостей/кэшей (`build`, `node_modules` и др.) применяются только к
каталогам: обычный tracked-файл вроде `scripts/build` остаётся в checkout.
Ссылки, Git hooks/logs и конфигурация remote не переносятся. `.git/config` заменяется минимальным
переносимым config без remote/credential. Все исключения перечислены, отдельно
показаны исключённые tracked-пути. Обычные файлы кода и документации о
credentials/secrets сохраняются. Это экспорт снимка для локального помощника,
а не резервная копия всех исходных метаданных. Стандартный host Git извлекает
реальные reachable objects в loose zlib layout; SHA, commit, branch/ref и shallow
границы сохраняются, история и HEAD не переписываются. Исходный pack целиком не
копируется, поэтому лишние недостижимые blobs/дельта-базы не переносятся.

Перенесите `.tar` в доступную файловому диалогу папку телефона. Откройте
«База знаний» в нужном проекте → «Импорт checkout .tar в пустой проект» →
выберите архив системным файловым диалогом. Приложение извлекает файлы в приватный
временный каталог, проверяет Git и публикует checkout целиком. Повторный импорт
поверх непустого проекта отклоняется. При ошибке извлечения корень остаётся пустым.

Поддерживается только несжатый USTAR: до 128 MiB архива и суммарного содержимого,
до 32 MiB на файл и 30000 записей. ZIP/gzip/PAX, абсолютные пути, traversal,
дубли путей без учёта регистра, ссылки и специальные файлы отклоняются.
Импорт требует самостоятельный `.git`, без `commondir` и object alternates.
Перед публикацией и при каждом чтении Git-контекста проверяются настоящие loose
objects: SHA-1/SHA-256, тип, длина, commit/tree/blob references и shallow boundaries.
Лимиты проверки: 32 MiB на decoded object, 128 MiB суммарно, 15000 объектов,
30000 ожидающих/проверенных ссылок и глубина 256. Потоковая распаковка прекращается
при превышении лимита. Gitlinks указывают на отдельные репозитории; их содержимое
не материализуется и не сертифицируется. Pack-only/неполные/повреждённые ODB
отклоняются явно; для них используйте host export и новый архив, также на desktop.
Provenance JSON — справочная запись, не замена проверке объектов и не подпись.

## Индекс и вопросы

1. Откройте «База знаний» выбранного проекта. Для desktop нажмите
   «Обновить README/docs проекта»; после Android-импорта этот корпус выбран автоматически.
2. Выберите корпус **README/docs проекта**, стратегию **Structure**,
   нажмите «Проверить модели», затем «Построить индекс».
3. Вернитесь в чат того же проекта и отправьте `/help <вопрос>` или `/help`.
   Переключать старый режим «По документам» для команды не требуется.
4. Раскройте карточку `mcp_project__git_branch` в обычном timeline:
   аргументы пустые, результат содержит project, branch, head, detached.
   Нажмите снова, чтобы свернуть. «Источники» открывает найденные фрагменты,
   реальные относительные пути, content revision и generation индекса.

Сканируются корневые README-варианты и текстовые `.md`, `.markdown`,
`.rst`, `.txt`, `.mdx` внутри корневых каталогов `docs`, `doc`, `documentation`, рекурсивно.
Набор корней можно инъецировать в native service. Вложенные demo/assets/docs
не принимаются за документацию проекта.
Скрытые файлы, `.git`, зависимости/кэши и `.pem/.key` не индексируются;
symlink не обходятся. Полный текст не сокращается молча: лимиты — 1000 документов,
4 MiB UTF-8 суммарно, 2 MiB на файл. При превышении или невалидном UTF-8 — ошибка.
Код в day31 сохраняется в checkout, но не входит в этот документационный корпус.

Идентичность источника — относительный путь, ревизия — SHA-256 нормализованного
текста. Содержимое и индексы хранятся в существующем JSONL, отдельно по project ID
и корпусу `project-docs-v1`. `/help` перечитывает текущие файлы перед каждым
вопросом и отклоняет устаревший/отсутствующий индекс. В базе знаний нажмите
«Обновить README/docs проекта», затем «Построить индекс»; добавления, изменения
и удаления отражаются в состоянии индекса. Готовый generation фиксируется на
время вопроса. Дополнительно к dense top-5 передаются первые два чанка каждого
корневого README (до 8000 UTF-8 байт в общем бюджете контекста). Они взяты из той
же generation и отмечены в трассе как `project_readme_overview`, без выдуманной
cosine-оценки. Все документы и чанки остаются в индексе; это навигационная опора
для общих вопросов о проекте. При смене проекта данные, история и provider continuation
предыдущего проекта не передаются в `/help`. Автоматическая compaction для такого
изолированного запуска отключена во всех точках (pressure, post-answer, overflow):
старый transcript не отправляется в summary-модель и не сокращается. Если текущий
изолированный запрос переполняет контекст, запуск завершится ошибкой без summary
retry; ранее сохранённая история остаётся на месте.

MCP зарегистрирован через существующую фабрику/SDK. Право на проект связано
со случайным scope конкретного запуска и не задаётся аргументами модели.
`/help` предлагает и разрешает только `git_branch`; read/write/edit/bash и
другие MCP-инструменты отсекаются runtime. Обычный чат и старые документные
режимы сохраняют свои правила; документные режимы остаются без инструментов.
Gitfile/worktree pointers читаются только внутри авторизованного корня.
Detached HEAD возвращает `branch: null`, отсутствие/неподдерживаемые metadata
возвращает ошибку инструмента — ветка по умолчанию не подставляется.

## Реальные сервисы и проверка

Нужна модель провайдера с поддержкой tool calls и обычный настроенный API-ключ
через существующее secure storage либо `DEEPSEEK_API_KEY`. Настройки ключей
для этой функции менять не требуется. Embeddings/tokenizer даёт существующий
`tool/rag_model_service`; его установка и запуск описаны в
[README сервиса моделей](../tool/rag_model_service/README.md). Используется настоящий Qwen embedding,
не hash/lexical fallback. Для M1 reranker не требуется. Недоступный сервис или
несовместимый индекс приводят к ошибке подготовки, обычный чат остаётся доступен.

Debug APK по умолчанию обращается к `http://127.0.0.1:8765`.
Для Android после запуска gateway координатор может настроить
`adb -s SERIAL reverse tcp:8765 tcp:8765`. Для другого endpoint задайте
`--dart-define=RAG_MODEL_BASE_URL=...` при сборке. Release требует HTTPS.

Опциональная проверка без изменения настроек/эмулятора использует настоящие
source tree, JSONL, production runtime/provider, embeddings и MCP SDK:

```sh
PROJECT_HELP_LIVE_ROOT=/absolute/standalone/checkout \
PROJECT_HELP_LIVE_REPORT=/tmp/project-help-report.json \
flutter test test/features/knowledge/application/project_help_live_test.dart
```

Gateway должен быть уже запущен, `DEEPSEEK_API_KEY` — доступен в окружении.
Ключ не печатается. Отчёт содержит actual source revisions, fingerprint,
выбранные фрагменты, результаты MCP и ответ. По умолчанию тест пропускается.
Это дополнительный smoke; Android UI и запись демонстрации проверяются отдельно.
