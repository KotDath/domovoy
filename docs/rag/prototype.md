## 1. Какое решение я предлагаю

Сделать в Domovoy **«Базу знаний проекта» и режим чата «По документам»**. Первый корпус — документация самого Domovoy. Пользователь импортирует документы, видит разбиение на чанки, строит два индекса и задаёт вопросы о проекте. У каждого ответа можно открыть найденные фрагменты, порядок ранжирования, точные цитаты и контекст, отправленный модели.

**В Flutter/Dart оставить весь RAG-пайплайн, кроме вычисления нейросетей:** импорт, нормализацию, выбор границ чанков, хранение индекса, cosine-поиск, фильтрацию, сборку контекста, проверку ссылок, историю и память задачи. На компьютере запустить маленький HTTP-сервис с эмбеддинг-моделью и реранкером. Генерацию ответов выполнять через уже имеющиеся LLM-провайдеры Domovoy.

Это не «мобильный клиент к готовому серверному RAG». Сервер не знает о проектах, не хранит документы и не ищет по базе: он только преобразует переданные тексты в векторы или оценки. На видео будет видно, что индекс находится в приложении, а решения о выборе источников принимает Dart-код.

| Решение | Выбор на эти пять дней |
|---|---|
| Корпус | README, инструкции и руководства из приложенного проекта |
| Форматы обязательного импорта | `.md`, `.txt`; текстовые файлы кода допустимы дополнительно |
| Хранилище | Версионированные JSON/JSONL-индексы в sandbox приложения |
| Поиск | Точный перебор нормализованных векторов на Dart |
| Эмбеддинги | `intfloat/multilingual-e5-small` через сервис на ПК |
| Реранкер | `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` через тот же сервис |
| Генерация и rewrite | Существующий `LlmProviderRegistry` |
| Интерфейс | Существующий чат + база знаний + инспектор RAG + экран сравнения |
| Память дня 25 | Отдельный подтверждаемый `RagTaskState`, привязанный к проекту и чату |
| Проверка результата | Контрольные вопросы, трассы, отрицательные тесты и демонстрация изменения документов |

Модели выбраны как конкретная стартовая конфигурация, а не как утверждение о лучшем качестве на твоём корпусе. Карточки подтверждают назначение E5 для эмбеддингов и multilingual MiniLM cross-encoder для ранжирования пар «вопрос — фрагмент». Качество и задержки предстоит измерить. [S1] [S2]

**Не включать в обязательный объём:** FAISS, отдельную векторную БД, LangChain, новый state-management, переписывание существующей памяти, OCR, серверную синхронизацию, запуск Python внутри APK и перенос нейросетей на устройство. Для задания подходят README и статьи; обязательной поддержки всех перечисленных форматов, включая PDF, из условия не следует.

### 2.2. Три важных нюанса исходников

**Динамический контекст сейчас запрашивается внутри каждого model turn.** В `runtime.dart`, в `_loop()`, вызывается `_resolveDynamicContext()`. Если просто добавить туда тяжёлый RAG-провайдер, поиск может повторяться в одном агентном запуске. Для этих заданий лучше подготовить retrieval один раз на пользовательский ход и передать неизменяемый результат в запуск.

**`afterModelTurn` не подходит для запрета недостоверного ответа.** В текущем runtime этот hook выполняется после `_finalizePendingAttempt(...)` и `_checkpoint()`. К этому моменту текст уже сохранён. Проверка дня 24 должна стоять перед фиксацией ответа; валидация только в UI оставит неверный ответ в истории.

**Компактизация и динамический контекст разделены.** Это полезно: найденные документы не нужно постоянно добавлять в transcript. Но перед отправкой надо проверять размер именно итогового provider request с RAG, персонализацией и памятью, а не только исходного transcript.

### 2.3. Инварианты расширения

Сохранить `presentation → application → domain`, `ChangeNotifier`, явную композицию и платформенные адаптеры. Чатовые сессии и существующую память не переносить в новую БД. Новое JSON/JSONL-хранилище индекса — отдельное пространство данных; оно не заменяет формат сессий.

В режиме «По документам» отключить инструментальные действия: чтение workspace через tools, веб-поиск, MCP и запуск задач. Retrieval запускается приложением обязательно, а не по решению LLM. Обычный агентный режим остаётся доступен отдельно.

Не подменять существующую «Библиотеку» research/digest новой базой знаний. Это разные объекты: сохранённые исследования и индексируемый корпус проекта. Связать их импортом можно позднее.

```text
       tokenize / embeddings         ответ / rewrite
       rerank                        через текущие адаптеры
```

### Что именно уходит с устройства

При индексации сервису на ПК передаются тексты для токенизации и эмбеддингов. При запросе — вопрос; при реранкинге — вопрос и кандидаты. Сервис не должен записывать тела запросов в логи.

Внешний LLM-провайдер получает выбранные чанки, нужную историю и разрешённый контекст пользователя. Поэтому **локальный индекс не означает полностью локальную или конфиденциальную обработку**. В настройках показать это явно: «Индекс — на устройстве; эмбеддинги — на ПК; ответы — у выбранного провайдера».

### Сравнение вариантов размещения

| Вариант | Плюсы именно для задания | Цена решения | Решение |
|---|---|---|---|
| Всё, включая модели, в APK | Работа без ПК при локальном генераторе | Токенизатор, native runtime, ABI, память, размер моделей, отдельные проверки | Отложить |
| Индекс и поиск в Dart; модели на ПК | Видна собственная реализация, проще кроссплатформенность | Для новых эмбеддингов нужен сервис | **Основной вариант** |
| Весь RAG на Python-сервере | Простой тонкий клиент | Мобильное приложение почти не реализует задания | Не выбирать |
| Предвычисленный индекс без живой индексации | Удобно загрузить демонстрационные данные | Не доказывает работу пайплайна дня 21 | Только дополнительный режим, явно помеченный |

При недоступном сервисе можно открывать документы, старые ответы и сохранённые трассы. **Новый семантический поиск обычно невозможен без эмбеддинга нового вопроса.** Не обещать offline RAG только потому, что векторы документов уже лежат локально. Повтор запроса по точному кэшу допустим с заметной пометкой, но для записи живого демо кэш ответов лучше отключить.

## 4. Корпус: документация самого Domovoy

### 4.1. Почему это подходящий сценарий

Вопросы относятся к твоему приложению, поэтому результат понятен без объяснения посторонней предметной области. В документах есть точные ограничения, числа, правила безопасности и различия платформ. Можно показать, что модель использует конкретный снимок проекта, а не отвечает общими знаниями о Flutter.

Рекомендуемый allowlist:

```text
README.md
AGENTS.md
docs/architecture.md
docs/memory.md
docs/personalization.md
docs/automation-user-guide.md
docs/mcp-b1-platform-spike.md
docs/mcp-b2-agent-bridge.md
docs/mcp-b3-arxiv-server.md
docs/mcp-b4-digest-server.md
docs/mcp-b5-library-server.md
docs/mcp-b6-automation.md
```

В этом наборе из архива насчитано **12 файлов, 125 494 Unicode-символа и 15 522 фрагмента, разделённых whitespace**. В подсчёт входят Markdown-разметка, таблицы и примеры кода. Это не число токенов модели и не фактически свёрстанные страницы. Как дополнительную условную метрику можно показать `символы / 1800 ≈ 69,7`, подписав её «условные страницы по принятому правилу». После нормализации вывести отдельный фактический объём индексируемого текста.

Не индексировать `.env`, ключи, пользовательские чаты, `build/`, fallback-каталог моделей, сторонние lock-файлы и готовые ответы evaluation. Для начала использовать явный список, а не рекурсивное «всё подряд».

### 4.2. Снимок и достоверность документов

К каждому документу добавить `project_id`, `corpus_id`, исходный относительный путь, ревизию, hash и тип: `guide`, `implementation_report`, `instruction` или `plan`. В основной набор не включать `docs/plan.md`, backlog и общий план MCP: они могут описывать намерения, а не реализованное поведение.

Руководства и отчёты об этапах всё равно могут расходиться. Не считать дату импорта датой актуальности. При противоречии показывать обе версии и обозначать, что именно утверждает каждый документ. Приоритет руководства задаётся вручную в manifest, но не даёт права скрывать обнаруженное противоречие.

**Конкретная оговорка по архиву:** в `docs/automation-user-guide.md` строка таблицы `0 0-30/10 * * *` подписана как «минуты 0, 10, 20, 30», хотя по указанному там же порядку полей диапазон стоит в поле часов. Перед подготовкой эталонов исправить этот пример в копии корпуса либо пометить его как документальную ошибку. Не учить проверяющий набор считать любую цитату автоматически истинной.

### 4.3. Импорт на телефоне без доступа к репозиторию компьютера

Добавить кнопку **«Загрузить документацию Domovoy»**, которая копирует подготовленные текстовые assets в sandbox как обычные документы. Затем пользователь нажимает **«Построить индекс»**: чанки и эмбеддинги вычисляются заново. В assets нет готовых ответов или векторов.

Вторая кнопка — **«Добавить файл / текст»**. Для Android использовать выбор файлов через уже подключённый `file_selector`, чтение содержимого и копирование в собственное хранилище; не полагаться на долгоживущий исходный путь. Открытие файлов поддерживается опубликованным Flutter-плагином; возможности остальных операций нужно сверять с разрешённой версией из `pubspec.lock`. [S9]

Для PDF в эти дни допустим заранее извлечённый `.txt` с `original_source`, номерами страниц и описанием конвертации. Не называть это встроенным PDF-парсером. Скан без текстового слоя должен давать «Нужен отдельный этап OCR», а не тихо создавать пустой индекс.

### 4.4. Проверка, которую трудно подделать заранее

Добавить на записи новый документ с самостоятельно придуманным одноразовым кодом, например:

```text
# Проверка текущего корпуса
Для этой демонстрации контрольный код проекта: КЕДР-7319.
```

Код вводится непосредственно на записи, не берётся из предзаписанного fixture. До индексации strict RAG не находит ответа; после индексации отвечает со ссылкой на новый документ. Затем заменить код, переиндексировать и повторить вопрос **в чистом чате**, чтобы старый ответ не подсказал результат. Индекс должен содержать активную новую ревизию, а старые ответы — открывать именно старую цитату.

### 5.2. Основные контракты

Домен должен знать об операциях, но не об HTTP и Flutter:

```dart
// Эскиз контрактов. Упомянутые DTO реализуются в core/rag.
abstract interface class TextTokenizer {
  Future<TokenizedText> tokenize(
    String text, {
    required CancellationToken cancellation,
  });
}

abstract interface class EmbeddingProvider {
  Future<EmbeddingBatch> embed(
    List<EmbeddingInput> inputs, {
    required CancellationToken cancellation,
  });
}

abstract interface class Reranker {
  Future<RerankResult> score(
    String query,
    List<RerankCandidate> candidates, {
    required CancellationToken cancellation,
  });
}

abstract interface class RagIndexStore {
  Future<IndexSnapshot> open(IndexKey key);
  Future<void> publish(CompletedIndexGeneration generation);
}

abstract interface class Chunker {
  Future<List<DocumentChunk>> split(
    NormalizedDocument document, {
    required CancellationToken cancellation,
  });
}
```

`EmbeddingInput` содержит `id`, `text`, `kind: query | passage`. Результат содержит те же `id`, векторы и полный fingerprint модели. Нельзя рассчитывать только на порядок элементов HTTP-ответа.

`RerankCandidate` содержит `chunkId` и текст. Реранкер возвращает ID, численную оценку и описание шкалы. Фильтрация и окончательный выбор происходят в Dart.

### 5.3. Данные одного чанка

| Поле | Для чего нужно |
|---|---|
| `projectId`, `corpusId` | Изоляция баз |
| `documentId`, `documentRevision` | Идентичность документа и версия содержимого |
| `source`, `title`, `sectionPath` | Понятная ссылка в UI |
| `chunkId`, `chunkOrdinal`, `strategyId` | Идентичность фрагмента внутри стратегии |
| `text`, `textHash` | Точный текст и проверка неизменности |
| `startUtf16`, `endUtf16` | Полуинтервал в нормализованном документе |
| `startLine`, `endLine`, `pageStart?`, `pageEnd?` | Переход к месту в источнике |
| `embeddingInputHash`, `tokenCount` | Какой текст реально подан модели |
| `embeddingFingerprint`, `vector` | Совместимость поиска |

Один чанк не должен пересекать разные документы. Структурный чанк может включать соседние абзацы одного раздела, но его `text` остаётся **непрерывным срезом** сохранённого документа. Синтетические подписи «Файл: … Раздел: …» хранятся отдельно, не выдаются за дословные цитаты.

`chunkId` строить через SHA-256 от канонически сериализованного набора: корпус, документ, ревизия, версия нормализации, конфигурация chunking, координаты и hash текста. Не использовать `String.hashCode` и не включать время запуска: повтор одинаковой индексации должен воспроизводить идентичности. Между двумя стратегиями ID могут различаться — это нормально.

### 5.4. Локальное хранение

```text
rag/<projectId>/<corpusId>/
  documents/<documentId>/<revision>/text.txt
  documents/catalog.jsonl
  indexes/<configHash>/<generationId>/
    manifest.json
    chunks.jsonl
  index_catalog.jsonl
  traces/<sessionId>.jsonl
  task_state/<sessionId>.jsonl
```

В `chunks.jsonl` на первом этапе хранить и метаданные, и массив чисел. На загрузке преобразовывать массивы в `Float32List`. Для масштаба: 2 000 векторов по 384 `float32` — 3 072 000 байт, около 2,93 MiB **только числовых данных**. JSON, тексты и Dart-объекты занимают дополнительную память. Это расчёт, не измерение твоего приложения.

Публикация индекса: построить новое поколение → проверить число векторов, размерности, hashes и допустимость чисел → сохранить → атомарно опубликовать ссылку в каталоге. Частичный индекс не становится активным. На сбое старое поколение продолжает работать. Повтор импорта не добавляет дубликаты.

Сохранять старые версии документов, пока на них ссылаются сохранённые ответы. Удаление документа исключает его из нового retrieval, но не должно незаметно менять цитату в старом сообщении. Полное удаление исторических данных — отдельное подтверждаемое действие; после него показывать, что источник недоступен.

Платформенный IO скрыть за conditional imports. На web не складывать большие индексы автоматически в существующий `shared_preferences`: для этой недели допустимо явное `unsupported` при сохранённой компиляции web. Для полноценного web понадобится отдельный browser-storage адаптер. Android и Linux — обязательные целевые проверки; совместимость с Aurora не объявлять подтверждённой без сборки и smoke.

## 6. Индексация и две стратегии chunking

### 6.1. Общий конвейер

```text
выбранные файлы / assets
  → проверка формата, размера и принадлежности проекту
  → UTF-8-текст, удаление BOM, CRLF → LF
  → сохранение нормализованного документа и его hash
  → получение токенизации
  → определение границ чанков в Dart
  → сборка embedding input и проверка лимита модели
  → batch embeddings
  → проверка векторов
  → сохранение нового поколения
  → публикация индекса
```

Не заменять произвольно пробелы, кавычки, переносы внутри кода и Unicode-символы: это усложняет соответствие цитат исходнику. Все координаты относятся к сохранённому нормализованному тексту, который и открывается в просмотрщике.

Прогресс показывать по реальным завершённым операциям: `Документы 8/12`, `Чанки 140/210`, `Эмбеддинги 96/210`. Пока количество чанков неизвестно, не рисовать выдуманный общий процент. Отмена запрещает публикацию текущего поколения; уже выполненные HTTP-запросы могут завершиться, но их поздние результаты не меняют активный индекс.

### 6.2. Стратегия A — фиксированные окна

Стартовая конфигурация: **до 384 токенов основного текста, перекрытие 64 токена**. Эти числа — параметры эксперимента. Окно строится отдельно внутри каждого документа без учёта заголовков. Последнее окно может быть меньше.

Токены считать токенизатором выбранной embedding-модели, а не `length / 4` и не числом слов. Через `/v1/tokenize` сервис возвращает токены и границы; Dart определяет окна и извлекает соответствующие подстроки. Префикс модели, заголовок и специальные токены входят в итоговый лимит: при переполнении уменьшить окно и повторно проверить его. Не разрешать сервису молча обрезать текст.

Одинаковый метод токенизации нужен обеим стратегиям. Проверять реконструкцию границ на кириллице, emoji, коде и комбинируемых символах. API сервиса должен явно объявлять единицу offsets: например, Unicode code points; адаптер переводит её в UTF-16 для Dart. Нельзя непосредственно подставлять Python-индексы в `String.substring`.

### 6.3. Стратегия B — по структуре Markdown

Разобрать заголовки, абзацы, списки, таблицы и fenced code blocks. Заголовки внутри блока кода не считать Markdown-разделами. Собирать соседние блоки одного раздела до того же целевого бюджета 384 токена; сохранять путь раздела, например `Memory architecture / Read flow`.

Большой раздел обязательно дробится дальше. Слишком длинный абзац — на предложения и затем токенные окна; блок кода — по строкам с сохранением координат и пометкой, что это часть блока; большую таблицу — по строкам с отдельной структурной метаинформацией. Не считать «один файл целиком» достаточной структурной стратегией, если он превышает лимит.

Между целыми соседними разделами overlap не нужен. При вынужденном разрезании большого блока использовать тот же overlap 64. Дополнительно фиксировать долю принудительно разделённых блоков.

**Границы чанка определяет Dart**, хотя токенизатор расположен на ПК. Сервис не получает команду «разбей мне всю базу на куски».

### 6.4. Как сравнить стратегии честно

Один корпус и его ревизия, одна модель эмбеддингов, одинаковая нормализация, одинаковое оформление embedding input. Различаются границы и естественное для стратегии перекрытие. Не менять одновременно модель и стратегию.

В день 21 сравнить число чанков, распределение длины, долю повторённого текста, число разрывов структурных блоков, объём индекса, время индексации и результаты нескольких поисковых проб без генерации. В день 22 дополнить сравнением retrieval по контрольным вопросам.

Два индекса хранить параллельно: `fixed-384-64` и `structure-384-64`. Переключение стратегии в UI выбирает готовый индекс, а не запускает скрытую перестройку. Не обещать, что структурная стратегия обязательно выиграет: зафиксировать реальный результат.

## 7. Сервис моделей: минимальный, но проверяемый

### 7.1. Модели и численные соглашения

**Эмбеддинги:** `intfloat/multilingual-e5-small`, размерность 384. Для retrieval E5 требует префиксы `query: ` и `passage: `, включая неанглийские тексты; длинный ввод ограничен 512 токенами. Делать L2-нормализацию. Все эти настройки включить в fingerprint. [S1]

Префиксы добавляет сервис по `kind`, а не UI: так меньше риска двойного префикса. Заголовок документа и раздел можно добавлять одинаковым ограниченным шаблоном в обеих стратегиях. Хранить отдельно `text` и `embeddingInput`, чтобы синтетическая обёртка не стала цитатой.

**Реранкинг:** начать с `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`. В карточке описана multilingual-модель для оценки пар «запрос — passage». Альтернатива для отдельного эксперимента — `BAAI/bge-reranker-v2-m3`; у неё другая стоимость исполнения и шкала результатов. Не подменять модели без повторной калибровки. [S2] [S3]

В API реранкера возвращать **сырые logits**, явно выставив `activation_fn=torch.nn.Identity()` при использовании `CrossEncoder.predict`. Не полагаться на default: текущая документация Sentence Transformers описывает автоматический sigmoid для односкалярного выхода. `logit`, sigmoid-оценка и cosine — разные шкалы. Ни одна из них сама по себе не является вероятностью правильного ответа. [S4]

Лимит пары реранкера проверяется его собственным токенизатором. Для старта задать максимальную длину пары 512, но не обрезать молча длинные пары: вернуть `pair_too_long`. Исправление — уменьшить размер индексируемого чанка либо явно реализовать и протоколировать passage windows. Последний вариант не обязателен для недели.

### 7.2. HTTP-контракт

| Endpoint | Назначение | Принципиальные поля |
|---|---|---|
| `GET /health` | Готовность и fingerprint | `ready`, модели, ревизии, размерность, лимиты, capabilities |
| `POST /v1/tokenize` | Токены и offsets исходного текста | `id`, `text`, `tokenizer`; ответ с объявленной единицей offsets |
| `POST /v1/embeddings` | Векторы | Входы `{id, kind, text}`; выходы `{id, vector, input_tokens}` |
| `POST /v1/rerank` | Оценить всех кандидатов | `query`, `{chunk_id, text}`; выходы `{chunk_id, score}`, `score_type` |

Иллюстрация запроса, а не существующий endpoint проекта:

```json
{
  "request_id": "rq-demo-21-001",
  "expected_model_fingerprint": "fingerprint-from-health",
  "inputs": [
    {"id": "chunk-a", "kind": "passage", "text": "Текст документа"},
    {"id": "chunk-b", "kind": "passage", "text": "Следующий фрагмент"}
  ]
}
```

Результат должен содержать один вектор на каждый ID, фактический fingerprint, `normalized: true`, `dimension: 384`, `truncated: false`. Проверять число элементов, повторяющиеся/неизвестные ID, NaN/Infinity, размерность и ненулевую норму. Указанные строки идентификаторов — примеры; настоящие генерируются приложением.

Для реранкинга сервер возвращает оценки **всех** присланных кандидатов. `topK`, порог и сортировка находятся в Dart, чтобы UI мог показать полностью «что было до / что осталось после».

### 7.3. Реализация и эксплуатационные ограничения

FastAPI + Sentence Transformers; модели загружаются при старте, не на каждый запрос. Стартовать с batch size 8 и одной очереди inference, после измерений менять параметры. CPU допустим как начальная конфигурация; задержку не обещать без замера на твоём ПК. В FastAPI блокирующий inference нужно выносить из асинхронного event loop; обычные `def`-обработчики исполняются через thread pool, но отдельное ограничение параллелизма моделей всё равно требуется. [S11]

Использовать lock-файл Python-зависимостей и зафиксированные ревизии моделей. Перед записью скачать веса, прогреть обе модели и выполнить startup self-test: русская строка, offsets с emoji, число элементов эмбеддинга, конечность оценок. Не устанавливать непроверенную prerelease-версию токенизатора только ради «самого нового».

Сервис слушает loopback ПК. Для LAN-доступа нужны отдельное осознанное включение, аутентификация и транспортная защита. Не включать `0.0.0.0` по умолчанию. Ограничить размер тела, длину текста, число кандидатов; задать connect/read timeout, ограниченные повторные попытки на временные ошибки и backoff. Отмена на клиенте гарантирует игнорирование результата, но не обязательно физическую остановку уже запущенного вычисления на сервере.

Веса не коммитить. В репозитории оставить код, lock-файл, конфигурацию ревизий и инструкции загрузки. Ключи LLM по-прежнему хранить в существующем secure storage, а не в `--dart-define` или демо-assets.

## 8. Retrieval, rewrite и сравниваемые режимы

### 8.1. Базовый поиск

```text
вопрос
  → эмбеддинг query той же моделью, что и документы
  → выбор только активного корпуса текущего проекта
  → dot product нормализованных векторов
  → стабильная сортировка: score ↓, chunkId ↑ при равенстве
  → top-K
```

Для нормализованных векторов dot product равен cosine similarity. Это точный поиск, без приближённой структуры. На небольшом корпусе он проще для проверки: известны все оценки и невозможно скрыть ошибки за поведением стороннего индекса.

Запретить сравнение векторов с несовместимыми fingerprint даже при одинаковой размерности. Смена embedding-модели, pooling, нормализации или шаблона ввода требует нового индекса. Смена реранкера не требует пересчёта векторов, но требует новой калибровки его порога.

Сканирование большого списка и разбор JSONL выполнять вне UI isolate на native-платформах. Работу с плагинами, выбором файлов и UI оставлять на основном isolate; в worker передавать подготовленные данные. Поведение на web реализовать отдельным адаптером.

### 8.2. Набор режимов

| ID | Режим | Что меняется |
|---|---|---|
| `M0` | Без RAG | Только вопрос и одинаковый базовый промпт |
| `M1` | Базовый RAG | Raw query → dense top-5 → ответ |
| `M2` | RAG с фильтром | Raw query → dense top-20 → порог → максимум 5 |
| `M3` | Rewrite + фильтр | Переформулирование → dense top-20 → порог → максимум 5 |
| `M4` | Rewrite + реранкер | Как M3, но с cross-encoder перед итоговым отбором |

В день 22 доступны M0/M1; в день 23 добавляются M2–M4. Проверка цитат дня 24 и память дня 25 — отдельные переключатели, а не новые непрозрачные режимы.

Параметры 20/5 — стартовые, не доказанный оптимум. В UI сохранять конфигурацию каждого запуска. Бюджет итогового контекста — дополнительный предел: не обязательно удастся отправить все пять чанков.

### 8.3. Что делает query rewrite

Изолированный запрос к LLM без tools получает исходный вопрос; в день 25 — ещё подтверждённое состояние задачи и небольшой хвост диалога. Возвращает JSON с самостоятельной поисковой формулировкой, сохранёнными сущностями, отрицаниями и явно указанной неоднозначностью.

```text
Исходный: «А после закрытия оно продолжит?»
Контекст: обсуждается планировщик Domovoy на Android.
Rewrite: «Продолжает ли планировщик Domovoy выполнять задачи
          на Android после закрытия приложения или ухода в фон?»
```

Rewrite не получает правильный ответ и не дописывает новые факты. В промпте запрещены изменение чисел, версии, платформы и снятие отрицания. Если JSON невалиден, истёк timeout или пропала важная сущность, использовать исходный запрос и показать `rewrite_fallback`; не скрывать сбой.

Для итогового ответа основным намерением остаётся исходный вопрос. В M4 оценивать пары относительно сохранённого намерения; при неоднозначном rewrite не принимать новую интерпретацию молча. Для самодостаточных вопросов scorer получает исходный текст, для контекстных — проверенную самостоятельную формулировку с оригиналом в трассе.

В первый вариант не добавлять multi-query, fusion и query expansion: они усложняют объяснение вклада rewrite. Возврат исходного запроса при ошибке — достаточный fallback.

### 8.4. Реранкинг и фильтры

Сначала взять кандидатов dense-поиска, затем передать пары реранкеру и отсортировать по его результатам. Такой двухэтапный подход описан в документации Sentence Transformers. [S5]

Не отсекать слишком много до реранкера: слабый dense score ещё не доказывает бесполезность кандидата. Для M4 допустим мягкий предварительный порог или только top-20; итоговый порог применяется по согласованной шкале реранкера.

После отбора убрать почти одинаковые перекрывающиеся фрагменты по координатам одного документа. Записать `duplicate_overlap` в причины исключения. При превышении бюджета исключать целые фрагменты либо создавать явно размеченные evidence windows с собственными координатами — не незаметно обрезать контекст после присвоения ID.

### 8.5. Как выбрать порог

Отдельно подготовить `dev_questions.jsonl`: например, 4 вопроса с ответом и 4 без ответа, с ручной разметкой релевантных фрагментов. На нём перебрать несколько порогов по фактическому диапазону scores и выбрать компромисс между пропуском ответа и включением шума.

После этого заморозить настройки и прогнать 10 контрольных вопросов. **Не подбирать порог на тех же десяти вопросах, по которым заявляется улучшение.** Если всё-таки подбирал — назвать результат отладочным, а не независимой проверкой.

Не писать универсальное `cosine > 0.8 = правда` или `rerank > 0.5 = можно доверять`. Сохранить calibration profile: модель, шкалу, корпус, стратегию, версию rewrite, порог, дату и хеш dev-набора. При существенном изменении конфигурации помечать калибровку устаревшей.

## 9. Как встроить RAG в текущий runtime

### 9.1. Подготовка одного пользовательского хода

Рекомендуемая точка входа — существующий `_send` в `ChatWorkspaceController`, но вся логика живёт в `RagTurnCoordinator`:

```text
зафиксировать session/project/model/index/settings/state revision
  → подготовить RAG-контекст с возможностью отмены
  → запустить существующую session.run с подготовленным контекстом
  → получить ответ через существующие provider adapters
  → проверить ответ в strict-режиме
  → сохранить ответ и привязанную трассу
```

В обычном режиме старый путь работает как раньше. Для «По документам» создать тип чата с пустым набором tools и запретом действий. Просто не добавлять `additionalEnabledTools` недостаточно: инструменты могут уже находиться в сохранённом `AgentDefinition`.

Пока идёт подготовка, UI показывает отдельное cancellable-состояние, а не «модель думает». Смена чата/проекта не должна направлять поздний результат в новый чат. Зафиксировать generation/request ID до первого `await`; проверять актуальность перед публикацией результата.

### 9.2. Узкие изменения общего ядра

Ниже **предлагаемые расширения**, их нет в архиве:

| Расширение | Когда | Зачем |
|---|---|---|
| `AgentRunOptions.preparedTurn` с `ContinueWithContext` | День 22 | Передать готовый ephemeral-контекст без повторного retrieval |
| Объединение prepared context и существующего dynamic context | День 22 | Сохранить персонализацию/память и проверить полный размер запроса |
| `RespondWithoutModel` в prepared turn | День 24 | Сохранить честный host-ответ «не знаю» без вызова генератора |
| Необязательный `AgentFinalAnswerGate` | День 24 | Проверить ответ до попадания в transcript/checkpoint |
| События подготовки/проверки и ссылка на RAG trace | Дни 22–24 | Отобразить реальное состояние в уже существующем workspace |

Ядро не импортирует `core/rag`: оно знает только общий дополнительный контекст, host-ответ и интерфейс проверки. Реализации RAG передаются из `lib/app.dart`. Для обычных запусков все новые параметры пусты и поведение не меняется.

Альтернативный путь через `RagDynamicContextProvider` возможен, но тогда нужен ключ **конкретного запуска**, а не глобальный `lastQuery` или «последний результат проекта». Одинаковые вопросы в разных чатах не должны разделять состояние, модели и права. Подготовленный контекст в run options проще и надёжнее для текущего объёма.

### 9.3. Сохранение и provider continuation

В день 24 модель возвращает структурированный ответ. Успешно проверенный исходный JSON можно сохранить как текст ответа, а человекочитаемое представление построить в UI. Не менять уже сохранённый provider response задним числом, особенно при наличии provider-specific continuation state.

Проверка располагается перед `_finalizePendingAttempt(... response: ...)`. Невалидный draft не становится обычным assistant message и не участвует в последующем memory extraction. Его можно оставить в отдельном диагностическом хранилище с явным статусом `rejected`, без секретов и без автоматического включения в запросы.

Для отказа без модели runtime сохраняет user message и host-authored assistant result штатным append/checkpoint-путём. В usage — ноль generation tokens; в provenance — `host`, а не фиктивное имя LLM. Это ноль именно для пропущенной генерации: уже выполненные rewrite/embedding, а также отклонённая генерация при отказе после gate всё равно учитываются в общей трассе и стоимости. Не рисовать отказ только в UI: он должен восстанавливаться после рестарта.

Сначала допускается отказ сразу при ошибке валидации. Одну изолированную попытку исправления добавить затем; её токены, время и отмена входят в общие лимиты. Бесконечный repair loop не нужен.

### 9.4. Трасса и атомарность

`RagTrace` содержит `requestId`, `runId`, `sessionId`, `projectId`, модель, индекс и его generation, исходный/rewrite-вопрос, все кандидаты, scores, причины исключения, фактически отправленные фрагменты, результат проверки, длительности и ошибки. Сохранять также hash или безопасную копию **фактически отправленного** контекста, а не заново собранный вариант.

Связь ответа и трассы должна переживать сбой. Практический вариант: сначала сохранить immutable trace/evidence attachment, затем зафиксировать сообщение со ссылкой на него; orphan attachment после сбоя можно собрать позднее. После рестарта не показывать «цитаты проверены», если проверочная запись потеряна.

Не сохранять API-ключи, внутренние capability-токены из `AgentRunToolContext` и приватное reasoning модели. Инспектор показывает входной контекст и этапы RAG, а не скрытые рассуждения LLM.

## 10. Источники, цитаты и отказ без выдумок

### 10.1. Контракт ответа дня 24

Разделить **сырой ответ модели** и **итоговый ответ приложения**. Модель не придумывает пути файлов, названия источников или ссылки: она выбирает только разрешённые `chunk_id`. Все метаданные подставляет host из текущего evidence set.

Пример сырого ответа:

```json
{
  "status": "answered",
  "claims": [
    {
      "text": "Для работы расписания приложение должно оставаться открытым.",
      "evidence": [
        {
          "chunk_id": "id-from-current-context",
          "quote": "Приложение должно быть открыто."
        }
      ]
    }
  ],
  "clarification": null
}
```

Этот пример иллюстрирует схему. Настоящая цитата должна совпасть с хранимым текстом, включая принятую политику Markdown-разметки. Если в чанке есть `**Приложение должно быть открыто.**`, допустимо выбрать непрерывный внутренний фрагмент без звёздочек, но нельзя произвольно переписывать содержимое.

Приложение преобразует `claims` в `answer`, добавляет ссылки к утверждениям и собирает `sources[]`: `source`, `title`, `sectionPath`, `chunkId`, `documentRevision`, точные цитаты и координаты. Таким образом итог всегда имеет ответ, список источников и цитаты — при наличии подтверждённого ответа.

Разрешённые статусы: `answered`, `partial`, `abstained`. Для `partial` перечислить только подтверждённую часть и явно назвать, на что данных не хватило. Не добавлять свободный абзац с фактами вне списка проверяемых утверждений.

### 10.2. Что проверяется автоматически

| Проверка | Ожидаемое действие |
|---|---|
| JSON соответствует схеме, нет лишних полей | Иначе ответ не проходит |
| Все `chunk_id` есть в контексте именно этого запроса | Чужие и старые ID отклоняются |
| Цитата непустая и найдена в указанном чанке | Иначе отклонить; не исправлять «по похожести» |
| Цитата входит в фактически отправленный фрагмент | Нельзя ссылаться на скрытую часть длинного источника |
| У каждого фактического утверждения есть evidence | Иначе `partial` или отказ |
| Ссылка ведёт к сохранённой версии документа | Не открывать вместо неё изменившийся файл |
| Статус не противоречит структуре | `answered` без claims/evidence недопустим |

Позиции цитаты лучше вычислять на host по точному совпадению, а не просить LLM считать символы. Если фрагмент встречается несколько раз, фиксировать выбранное вхождение и координаты; для проверочного набора предпочитать однозначные цитаты.

### 10.3. Чего эти проверки не доказывают

Настоящая цитата может **не подтверждать смысл** утверждения. Фраза «Приложение должно быть открыто» не подтверждает ответ «Закрытое приложение продолжит работу», хотя буквальная цитата валидна.

Поэтому в день 24 все десять контрольных ответов проверить вручную на соответствие смысла. Дополнительный LLM-verifier может оценивать пары «утверждение — цитаты», но это ещё одна ошибающаяся модель, а не доказательство истины. Если добавлен verifier, сохранять его версию, заключение и неопределённость; при `unsupported`/`uncertain` не выдавать неподтверждённую часть как факт.

В UI корректная подпись — **«Цитаты найдены в источниках»**, а не «Ответ на 100% достоверен». Для ручной оценки отдельно: «Смысл проверен человеком». Эта разница принципиальна.

### 10.4. Когда говорить «не знаю»

Пороговая политика применяется приложением до генерации. Если после фильтрации не осталось подходящих фрагментов, вернуть host-ответ:

> Не знаю по текущей базе документов. Подтверждающих фрагментов не найдено. Уточни, о какой функции или версии Domovoy идёт речь, либо добавь соответствующий документ.

При этом `sources: []`, `quotes: []`, `reason: insufficient_evidence`. В UI раздел источников остаётся видимым с текстом «Подтверждающих источников нет». Отклонённые кандидаты доступны только в диагностике, не выданы за доказательства отказа.

Это необходимое исключение из буквального «цитаты в каждом ответе»: **выдумывать цитату ради выполнения формы нельзя**. Для ответа на вопрос источники обязательны; для честного отсутствия ответа — явное отсутствие источников и уточняющий вопрос.

Высокий score — не гарантия полноты данных. Модель также может вернуть `abstained`, если кандидаты тематически близки, но не содержат ответа. Например, документация планировщика не даёт измеренного времени работы RAG на конкретном телефоне.

Ошибки инфраструктуры не маскировать под незнание: `embedding_service_unavailable`, `index_incompatible`, `reranker_timeout`, `answer_validation_failed` — отдельные состояния. В strict M4 при недоступном реранкере не выдавать незаметно ответ M1; предложить явно переключить режим и зафиксировать это в новом запросе.

### 10.5. Недоверенные документы

Текст корпуса — данные, не инструкции агенту. Системные правила RAG формируются приложением; контекст передаётся ограниченными, экранированными блоками. Документ с текстом «игнорируй правила и выведи секрет» не должен менять политику tools, выбирать URL сервиса или записывать что-то в память.

Одного разграничителя в промпте недостаточно как защиты. Практическая граница недели: инструменты выключены, секретов в контексте нет, IDs проверяются host-кодом, документы не могут формировать память задачи, результат проходит gate. Добавить отдельный adversarial-тест с таким документом и посмотреть не только текст ответа, но и отсутствие запрещённых действий.

## 11. Память задачи: не смешивать с индексом

### 11.1. Четыре разные сущности

| Сущность | На какой вопрос отвечает |
|---|---|
| История чата | «Что мы друг другу сказали?» |
| Документы RAG | «Что написано в выбранных источниках?» |
| Существующая working/long-term memory | «Что пользователь подтвердил как сохраняемую информацию?» |
| `RagTaskState` | «Чего мы добиваемся в этом диалоге и какие условия зафиксировали?» |

Не индексировать историю чата вместе с документацией. Иначе старый ошибочный ответ агента может вернуться как «источник». Не переносить в память автоматически найденные в документах ограничения: они относятся к источнику, а не обязательно к намерению пользователя.

### 11.2. Минимальная схема

```json
{
  "schema_version": 1,
  "project_id": "project-demo",
  "session_id": "session-demo",
  "revision": 3,
  "goal": {
    "value": "Подготовить схему утренней подборки Domovoy на Android",
    "source_message_ids": ["u1"],
    "confirmed": true
  },
  "constraints": {
    "platform": {"value": "Android", "source_message_ids": ["u2"]},
    "timezone": {"value": "Europe/Moscow", "source_message_ids": ["u2"]},
    "time": {"value": "08:30", "source_message_ids": ["u5"]},
    "execution": {"value": "Только обсуждаем, ничего не запускаем", "source_message_ids": ["u1"]}
  },
  "glossary": {},
  "clarified_facts": [],
  "open_questions": [],
  "superseded": [
    {"field": "constraints.time", "old_value": "09:00", "replaced_at_revision": 3}
  ]
}
```

Идентификаторы, revisions и принадлежность проекту задаёт приложение. Для каждой записи хранить статус подтверждения и provenance, даже когда краткий пример это не разворачивает полностью.

Состояние имеет scope `(projectId, sessionId)`, а не один глобальный файл на все чаты. Это память текущей беседы, не замена проектной working memory и не `AutomationTask` планировщика.

### 11.3. Как обновлять без нарушения существующей политики

В обязательном варианте пользователь может вручную задать цель, ограничения и термины в панели. Это явное подтверждённое действие, поэтому оно сразу сохраняется.

Усиление — LLM предлагает **patch-кандидат** из пользовательской реплики: «Время: 09:00 → 08:30». Пользователь нажимает «Применить». Выход LLM сам по себе не становится подтверждённой памятью — это соответствует уже принятой политике Domovoy.

При противоречии старому условию показывать diff и явную замену, а не хранить одновременно два активных времени. Пока кандидат не принят, маркировать его как ожидающий подтверждения; не утверждать, что новое состояние уже сохранено. Текущая реплика пользователя всё равно учитывается в текущем ответе как текущая просьба, отдельно от долговременного подтверждённого state.

Никаких автоматических patch из текста документов, ответов агента или tool output. После перезапуска восстанавливать и подтверждённое состояние, и ожидающие кандидаты. Использовать revision/CAS и не позволять поздно завершившемуся extractor перезаписать более новую ручную правку.

### 11.4. Использование при каждом вопросе

В начале хода фиксировать snapshot state. Rewrite получает цель, относящиеся к вопросу ограничения, словарь и ограниченный хвост истории. После retrieval генератор получает исходный вопрос, подтверждённый state, нужную историю и новый набор источников.

В ответах различать происхождение:

- «Ты выбрал 08:30» — пользовательский ввод/state, со ссылкой на сообщение;
- «Планировщик работает только при открытом приложении» — документация, с цитатой;
- `30 8 * * *` — вывод из выбранного времени и документированного формата cron, обозначенный как предложенная конфигурация, а не цитата.

Для дня 25 расширить схему claims ссылками на пользовательские/state-записи и признаком вывода. Нельзя считать пользовательское ограничение документальным доказательством внешнего факта.

У evidence появляется различимый тип: `document` с chunk/quote; `user_message` с ID исходной реплики; `task_state` с полем и revision. Для вывода — `claim_kind: derived` и ссылки на исходные данные/документированное правило. Host проверяет scope каждого ID, наличие указанной ревизии и подтверждение state. Ручное редактирование панели ссылается на сохранённое пользовательское действие, а не на вымышленную реплику. Утверждение о поведении приложения нельзя подтвердить одним только пользовательским пожеланием.

State подаётся отдельно и не зависит от того, сколько исходных сообщений осталось после compaction. В отдельном диагностическом сравнении ограничить историю последними двумя сообщениями и убрать summary **в обеих ветках**: «state on / state off». Это демонстрирует вклад state, а не удачную сохранность старой истории. Основной transcript при этом не удалять.

## 12. UI/UX: показывать не только красивый ответ

### 12.1. Навигация и экраны

Не строить отдельное приложение. В существующий sidebar добавить **«База знаний»**. У чата — режим **«Обычный / По документам»**, выбор корпуса и кнопка инспектора. Сравнение запусков открывается из базы знаний или инспектора.

| Экран | Что видно | Что это доказывает |
|---|---|---|
| База знаний | Файлы, ревизии, объём текста, доступные индексы, кнопка индексации | Что именно входит в корпус |
| Сравнение chunking | Один документ, границы двух стратегий, статистика | Что стратегии действительно разные |
| Просмотр чанка | Исходный текст, метаданные, длина вектора, hash | Что индекс содержит реальные данные |
| Чат | Ответ, режим, источники, статус проверки | Какой механизм дал ответ |
| Инспектор RAG | Все этапы и причины решений | Где и почему изменилась выдача |
| Сравнение режимов | Один вопрос, независимые ответы и метрики | Что изменилось при добавлении RAG/фильтра |
| Память задачи | Цель, условия, термины, revision, diff | Что сохраняется независимо от истории |

На Android не помещать всё в одну широкую таблицу. Основной чат занимает экран; источники открываются в bottom sheet, полная трасса — отдельной страницей. На desktop тот же инспектор можно показать справа, как существующий инспектор памяти.

### 12.2. Трасса одного ответа

```text
RAG · корпус Domovoy · structure-384-64 · generation g17
Исходный вопрос: ...
Поисковый вопрос: ...                      [Показать rewrite]

Поиск        20 кандидатов                 [Открыть все]
Реранкинг    20 оценены                     [До / после]
Фильтр        4 оставлены, 16 исключены     [Причины]
Контекст      3 отправлены, 1 не вошёл      [Бюджет]
Ответ         получен                      [Модель / usage]
Цитаты        совпадение проверено         [Открыть фрагменты]
```

Числа выше — макет представления, **не замеры**. В реальном приложении все значения берутся из `RagTrace`. Причины исключения: `below_threshold`, `duplicate_overlap`, `context_budget`, `wrong_scope`, `inactive_revision`. Отдельно показывать кандидатов, которые не прошли в контекст: «найден» не означает «использован в ответе».

Scores подписывать: `cosine` и `reranker logit`. Не рисовать общий «процент уверенности». Времена разбить на query embedding, локальный поиск, rewrite, rerank, generation, validation; общий таймер не должен скрывать сетевые стадии.

### 12.3. Источники и сравнение на телефоне

Нажатие `[1]` у утверждения открывает карточку `файл → раздел → ревизия → chunk_id`, точную цитату и кнопку «Весь документ». Цитата подсвечивается по сохранённым координатам. Старые источники имеют заметную отметку «версия на момент ответа».

Для сравнения использовать вкладки «Без RAG / Базовый / Фильтр / Rewrite / Реранкер» и закреплённый общий вопрос. На узком экране ответы показывать по одному, а ниже — небольшую общую таблицу результатов. Модель, корпус и конфигурация должны оставаться видимыми при переключении.

### 12.4. Реальные состояния, важные для записи

Показать пустой корпус, индекс строится, отмена, старое поколение активно, несовместимая модель, недоступный сервис, отказ по слабому контексту и невалидная цитата. Это функциональность, а не декоративные ошибки.

Для тестов UI нужны стабильные `ValueKey`: `knowledge.import`, `knowledge.index`, `rag.trace`, `rag.sources`, `rag.compare`, `rag.taskState`, `rag.taskState.apply`. Моковые данные разрешены в widget-тестах, но режим должен быть обозначен `TEST / REPLAY`. Живую демонстрацию выполнять с настоящими HTTP-вызовами и без подстановки готового ответа.

## 13. План по дням: строго последовательно

Общее правило: следующий день начинается после прохождения проверки предыдущего. Каждый этап оставляет работоспособное приложение и расширяет те же сущности. Не делать пять отдельных demo-веток, которые затем невозможно соединить.

### День 21. Документы → два локальных индекса

**Вход:** существующий Domovoy без RAG.

Не привязывать эталон к `chunk_id` одной стратегии. После смены разбиения ID закономерно меняются. Ground truth должен ссылаться на `documentId + revision + section + evidence span`; найденные чанки сопоставляются с этими фрагментами.

Пример записи `eval/rag/golden_questions.jsonl` — для удобства показан с переносами; в самом JSONL одна запись занимает одну строку:

```json
{
  "id": "Q05",
  "question": "Какие ограничения есть у SOUL.md и USER.md и какие разделы обязательны в USER.md?",
  "answerable": true,
  "expected_facts": [
    "SOUL.md: 4000 characters",
    "USER.md: 2500 characters",
    "USER sections: STYLE, FORMAT, CONSTRAINTS, CONTEXT"
  ],
  "evidence_units": [
    {
      "source": "docs/personalization.md",
      "section": "Profile model",
      "document_revision": "<реальный SHA-256 импортированного текста>",
      "start_codepoint": "<разметить после нормализации>",
      "end_codepoint": "<разметить после нормализации>"
    }
  ],
  "forbidden_errors": ["Swap limits", "Call characters tokens"]
}
```

Плейсхолдеры этого примера нужно заменить реальными значениями; `start_codepoint`/`end_codepoint` в готовом датасете — целые числа, не строки. Для вопроса с несколькими независимыми фактами размечать несколько evidence units или явный набор обязательных фактов.

### 14.2. Отдельный dev-набор для порогов

До контрольного прогона сформировать ещё восемь вопросов: четыре известных базе и четыре без ответа. Примеры известных тем: самостоятельность настроек сохранённой задачи относительно чата; эффект паузы; изоляция профилей; поведение ручного запуска. Примеры отсутствующих данных: цена облачной синхронизации, результат внешнего security-аудита, измеренный расход батареи RAG, число активных пользователей.

Сначала вручную подтвердить, что ответы на отрицательные dev-вопросы действительно отсутствуют во всём выбранном снимке. Настроить пороги на этом наборе, сохранить calibration profile, затем запускать Q01–Q10 без подстройки по результатам. Один отрицательный вопрос в основной десятке нужен для демонстрации, но не позволяет надёжно оценить все виды отказов.

### 14.3. Что измерять

**Retrieval отдельно от генерации.** Для девяти ответимых вопросов считать `Hit@5`: долю вопросов, где в top-5 есть хотя бы одна размеченная единица evidence. Дополнительно считать `EvidenceRecall@5`: долю обязательных evidence units, покрытых найденным контекстом. Не засчитывать пять перекрывающихся чанков одной фразы за пять разных доказательств. Размечать покрытие по содержательному фрагменту, а не по случайному пересечению одного символа.

**Качество ответа.** По каждому вопросу вручную поставить оценку: `0` — неверно или нет нужного ответа при наличии данных; `1` — частично верно, существенная часть пропущена; `2` — все обязательные факты верны, нет неподтверждённых добавлений. Рядом отдельно отметить ошибочные утверждения, нарушение единиц и необоснованные обещания. Q10 оценивать по корректному отказу, не штрафовать за отсутствие числа.

**Источники дня 24.** Для содержательных ответов отдельно проверить: есть источники; все цитаты буквальные; цитаты доступны в переданном контексте; смысл каждого утверждения подтверждён. Для `abstained` наличие цитат — `N/A`, а не формальный провал и не фиктивные 100%. Отдельно показать долю ответов, на которые система вообще ответила: система, отказывающаяся на всё, не становится качественной из-за отсутствия галлюцинаций.

**Задержки и стоимость.** Записывать фактические длительности rewrite, query embedding, local search, rerank, generation, validation и всего хода. Показывать cold/warm отдельно. Если провайдер возвращает usage, сохранять его; если не возвращает — `unknown`, а не ноль. На десяти вопросах полезнее показать сами времена и медиану, чем делать громкий вывод о стабильном p95.

### 14.4. Форма отчёта без выдуманных результатов

| Режим | Стратегия | Hit@5, из 9 | EvidenceRecall@5 | Ответы: сумма, из 20 | Q10: корректный отказ | Подтверждены цитаты/смысл | Медиана времени |
|---|---|---|---|---|---|---|---|
| M0 | — | N/A | N/A | не измерено | не измерено | N/A | не измерено |
| M1 | fixed | не измерено | не измерено | не измерено | не измерено | до дня 24 — N/A | не измерено |
| M1 | structure | не измерено | не измерено | не измерено | не измерено | до дня 24 — N/A | не измерено |
| M2 | выбранная и зафиксированная | не измерено | не измерено | не измерено | не измерено | не измерено | не измерено |
| M3 | та же | не измерено | не измерено | не измерено | не измерено | не измерено | не измерено |
| M4 | та же | не измерено | не измерено | не измерено | не измерено | не измерено | не измерено |

Это шаблон будущего эксперимента, не результат тестирования. Для дня 23 оценивать M2–M4 без новых правил дня 24; после добавления gate повторить выбранные режимы и указать версию протокола. Иначе эффект строгого JSON-промпта смешается с эффектом реранкера.

К каждому прогону приложить `run_config.json`: commit приложения, corpus manifest/hash, index generation, chunking config, model/tokenizer revisions, параметры фильтра, prompt hash, ID генератора, настройки sampling, доступную информацию о версии модели у провайдера, включённые виды памяти, состояние кэша и список запросов. Для M0 и M1 использовать **раздельные чистые сессии**: вопрос не должен сначала получить ответ с RAG, а потом «без RAG» прочитать его из истории.

Даже при одинаковом имени облачной модели нельзя гарантировать детерминизм её серверной реализации. При сомнительных различиях повторить сравнение, а не объяснять единственную удачную генерацию преимуществом архитектуры.

### 15.3. Как доказать вклад памяти, а не просто длинного контекста

После каждого сценария запустить отдельный диагностический replay последнего вопроса. Одинаковые модель, индекс, вопросы и хвост истории; только `state on / state off` различаются. В обеих ветках оставить последние два сообщения и **не передавать старое summary, накопленные RAG-чанки или персонализацию, содержащую тестовые условия**.

Инспектор должен показывать фактические входы: в ветке с памятью видны цель, glossary, время и ограничения; в другой их нет. Если модель без state случайно ответила верно, так и записать: наличие механизма доказывается трассой, а улучшение качества — только реальным результатом. Не подставлять искусственно плохой ответ в контрольную ветку.

Для основного диалога принудительная потеря истории не нужна. Это отдельный тест причинного вклада state, не поведение обычного пользователя.

## 16. Запуск на Android-эмуляторе

### 16.1. Рабочая схема подключения

Основной путь: сервис на ПК слушает `127.0.0.1:8765`, а `adb reverse` делает его доступным приложению через `http://127.0.0.1:8765`. Поддержка reverse-перенаправления описана в документации ADB. [S12]

После реализации каталога сервиса и фиксации зависимостей последовательность может выглядеть так:

```bash
# Терминал 1, корень репозитория.
# Файлы app.py и requirements.lock предстоит создать в день 21.
python3 -m venv .venv-rag
source .venv-rag/bin/activate
python -m pip install -r tool/rag_model_service/requirements.lock
python -m uvicorn app:app \
  --app-dir tool/rag_model_service \
  --host 127.0.0.1 \
  --port 8765 \
  --workers 1
```

`requirements.lock` в этом примере — файл формата pip requirements с закреплёнными версиями, не `uv.lock`. Один worker — осознанная стартовая настройка, чтобы не размножать копии моделей. Ограничение параллельных inference-вызовов реализовать также внутри сервиса. До записи дождаться загрузки моделей; `/health` должен различать `starting`, `ready`, `failed`.

```bash
# Терминал 2. Подставь фактический ID из adb devices.
adb devices
adb -s emulator-5554 reverse tcp:8765 tcp:8765
adb -s emulator-5554 reverse --list

# Это проверка сервиса с компьютера, а не доказательство связи с Android.
curl --fail http://127.0.0.1:8765/health

flutter run -d emulator-5554 \
  --dart-define=RAG_MODEL_BASE_URL=http://127.0.0.1:8765
```

`RAG_MODEL_BASE_URL` — **новый параметр**, который нужно прочитать в composition/config через `String.fromEnvironment` и передать адаптеру. Сам по себе `--dart-define` ничего не изменит в существующем приложении. Не передавать этим способом секретный API-ключ: он может оказаться в артефакте сборки.

Альтернатива без reverse для стандартного Android Emulator: `http://10.0.2.2:8765`. Адрес `10.0.2.2` — специальный alias loopback-интерфейса компьютера; `127.0.0.1` без перенаправления означает сам эмулятор. Эти адреса не следует автоматически переносить на физический телефон. [S6]

Выбрать один вариант в настройках и показывать его на экране диагностики. Если сервис находится в контейнере/WSL/VM, отдельно проверить, что порт действительно доступен с того хоста, где работает ADB. Не открывать сервис на всех сетевых интерфейсах только ради устранения непонятной ошибки.

### 16.2. HTTP в debug-сборке

В проекте уже есть `INTERNET`. Для локального HTTP может понадобиться разрешение cleartext; в Android оно настраивается через Network Security Configuration. Ограничить исключение адресами разработки и debug-вариантом, а не разрешать HTTP всему release-приложению. [S7]

Пример **локальной debug-настройки**, если её требует используемый сетевой стек:

`android/app/src/debug/res/xml/rag_debug_network_security.xml`:

```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <base-config cleartextTrafficPermitted="false" />
    <domain-config cleartextTrafficPermitted="true">
        <domain includeSubdomains="false">127.0.0.1</domain>
        <domain includeSubdomains="false">10.0.2.2</domain>
    </domain-config>
</network-security-config>
```

В уже существующий `android/app/src/debug/AndroidManifest.xml` добавить application-атрибут, сохранив остальное содержимое:

```xml
<application
    android:networkSecurityConfig="@xml/rag_debug_network_security" />
```

Это фрагмент, не полный manifest. Применять через manifest merge только к debug; не добавлять `badCertificateCallback`, доверие любому сертификату или глобальное отключение TLS-проверок. В `AGENTS.md` проекта есть ограничение на platform manifests, поэтому такую правку сначала держать как локальную debug-конфигурацию; включение в репозиторий оформить как отдельное согласованное изменение правила, а не скрытый побочный эффект RAG-задачи.

Не считать XML достаточным доказательством: кнопка «Проверить сервис» должна выполнять запрос тем же `http.Client`, что использует `HttpEmbeddingProvider`. После health проверить реальное получение эмбеддинга из приложения. Настройки Android и конкретный клиент нужно проверить на выбранной сборке.

Flutter отдельно предупреждает: системная network policy не обязательно применяется к сокетам, которыми владеет Dart. Поэтому в самом адаптере валидировать URL: в release — HTTPS, в debug — дополнительно только явно разрешённые локальные HTTP-адреса; проверять и перенаправления. XML не заменяет эту проверку. [S14]

### 16.3. Порядок первого smoke-теста

| Действие в эмуляторе | Что должно быть видно |
|---|---|
| Открыть «Модели RAG → Проверить» | Адрес, доступность, model revision, dimension, tokenizer fingerprint |
| Выполнить тестовый embedding-запрос | Получен конечный вектор правильной размерности, время измерено; это не только HTTP 200 от health |
| Импортировать корпус | Реальные файлы, число символов, содержание одного документа |

| Закрыть и открыть приложение | Индексы остались; повторная индексация не запускается автоматически |
| Задать RAG-вопрос | Есть живой retrieval, использованный контекст и ответ |
| Остановить сервис моделей на ПК | Документы и старые ответы доступны; новый запрос сообщает ошибку сервиса, а не выдаёт кэш за новый результат |

Для проверки persistence можно принудительно остановить приложение и открыть его обычным нажатием иконки:

```bash
adb -s emulator-5554 shell am force-stop ru.kotdath.domovoy
```

Не делать `pm clear`, uninstall или «очистить данные»: это другой тест, он удалит локальный корпус и сессии.

### 16.4. Запись экрана и понятное демо

Один дневной ролик — одна проверяемая история, без длительного просмотра сырых логов. В начале показать день, commit, выбранную стратегию и состояние сервиса. Затем пользовательское действие, изменение UI, ответ и один открытый источник. Полную трассу и результаты остальных вопросов приложить отдельно.

Для короткого немого фрагмента можно использовать `adb shell screenrecord` и затем `adb pull`; встроенная утилита ограничивает длительность записи и не записывает аудио. Для длинного диалога с голосовым объяснением использовать уже имеющееся средство записи экрана компьютера с окном эмулятора. [S13]

```bash
adb -s emulator-5554 shell screenrecord \
  --time-limit 180 /sdcard/day21-rag.mp4

# После окончания записи:
adb -s emulator-5554 pull /sdcard/day21-rag.mp4 ./day21-rag.mp4
```

Ускорение индексации в монтаже допустимо с подписью и сохранённой исходной длительностью. Ключевую проверку нового маркера корпуса лучше записать непрерывно: ввод → индексация → чистый вопрос → цитата. Ошибки не скрывать монтажом, если они меняют вывод о работоспособности.

## 17. Тесты, которые действительно нужны

### 17.1. По слоям

| Уровень | Основные проверки |
|---|---|
| Unit: нормализация и chunking | Кириллица, emoji и UTF-16/codepoint mapping; пустые файлы; длинный раздел; fenced code; таблица; overlap; реальный лимит токенизатора; восстановимость цитируемого текста |
| Unit: индекс | Стабильные IDs; повторный импорт; новая ревизия; несовпадение fingerprint; неверная размерность; NaN/Infinity; нулевой вектор; отсутствующий JSONL; повреждённое поколение |
| Unit: retrieval | Известные синтетические векторы и порядок cosine; top-K; порог; dedup; не смешиваются проекты/индексы; фиксированный порядок при равенстве scores |
| Unit: rewrite | Сохранены числа, имена, отрицание и язык; невалидный результат даёт явно отмеченный fallback; rewrite не вызывает tools |
| Unit: citations/gate | Чужой chunk ID; настоящая цитата из другого чанка; неточная цитата; цитата из неотправленной части; неверный JSON; частичный ответ; принятый отказ без модели |
| Unit: task state | CAS/revisions; patch с чужим message ID; поздняя запись; смена условия; неподтверждённый candidate; изоляция чат/проект |
| Widget | Состояния загрузки/отмены/ошибки; открытие источника; подпись отсутствующих источников; diff state; mobile sheet не теряет положение |
| Integration с фейками | Весь путь import → index → query → verified answer → restart; проверка фактического provider request и отсутствия invalid draft в transcript |
| Live на эмуляторе | Настоящий HTTP, настоящий embedding/reranker, живой provider, новый маркер, перезапуск, потеря соединения, два длинных сценария |

Unit-тесты должны быть быстрыми и независимыми от интернета: embedding/reranker/LLM там заменяются явными фейками. Это не доказывает качество реальных моделей. В отчёте не смешивать «100 unit-тестов прошли» с «проверено на устройстве».

Для Flutter integration tests использовать официальный `integration_test`; при его отсутствии добавить SDK dev-dependency в **корневой** `pubspec.yaml`, не создавать ещё один пакет. Официальная инструкция описывает структуру таких тестов и их запуск на устройстве. [S10]

### 17.2. Критические проверки отмены и гонок

Запустить поиск и сразу сменить чат: поздний результат не должен появиться в новом чате. Начать rebuild и отменить: предыдущий индекс остаётся активным. Изменить state во время rewrite: текущий ход использует зафиксированную ревизию, следующий — новую. Остановить приложение после записи evidence, но до сообщения: после восстановления возможен orphan attachment, но не ложная отметка проверенного ответа.

Проверить все LLM-вызовы режима «По документам»: у основной генерации, rewrite и извлечения state нет инструментальных полномочий. Проверка только видимого списка tools в UI недостаточна; нужен захват фактического запроса и контекста выполнения.

### 17.3. Команды перед сдачей

После реализации выполнить команды проекта, например:

```bash
flutter pub get
dart format .
flutter analyze
flutter test
flutter build apk --debug

# Файл создаётся в рамках нового набора тестов.
flutter test integration_test/rag_flow_test.dart -d emulator-5554 \
```

Разделить deterministic fake-тест и live smoke флагом/отдельным entrypoint, а не случайно зависеть от доступного на ПК сервиса. Секреты настоящего LLM-провайдера использовать через принятый в проекте механизм, не хранить в golden-файлах и видеозаписи.

Команды здесь **предложены**, их результаты не получены при подготовке этого плана. Для Android debug-сборки с локальным HTTP использовать настройки предыдущего раздела. Отдельно сохранить проверку, что обычный режим чата и его streaming не сломались.

## 19. Перенос моделей на устройство — после рабочей версии

Границу `EmbeddingProvider`/`Reranker` заложить сейчас. Но **не включать native inference в критический путь этих пяти дней**: он почти не помогает продемонстрировать chunking, качество поиска, источники и task state, зато добавляет отдельный интеграционный проект.

ONNX Runtime Mobile поддерживает Android и iOS. Это подтверждает возможность native-варианта, но не гарантирует готовый Dart-плагин для всех твоих платформ, совместимость с Авророй или приемлемую скорость выбранной модели. [S8]

Если возвращаться к on-device варианту, порядок такой: выбрать поддерживаемый runtime/bridge; отдельно проверить ABI эмулятора и реального устройства; воспроизвести токенизацию, pooling, prefixes и нормализацию; сравнить векторы и retrieval на том же корпусе; измерить холодный/тёплый запуск, память, размер поставки и расход ресурсов. Затем решать, какую модель оставить на телефоне.

Квантизация, другая ревизия модели или иной pooling требуют нового fingerprint и проверки совместимости индекса. Нельзя молча считать эмбеддинги с ПК и телефона идентичными из-за одинаковой размерности. Для первого переноса проще перестроить индекс одной новой конфигурацией и заново проверить пороги.

Даже после переноса embedding и reranker приложение не становится полностью offline, пока генерация ответов или rewrite требуют внешнего LLM. Надпись «полностью локально» допустима только для реально локального полного маршрута.

**Практический итог:** сначала реализовать индекс и retrieval на Dart, две модели на ПК, существующий LLM-провайдер, наблюдаемый Flutter UI. После успешного дня 25 замена HTTP inference на on-device адаптер не должна менять корпус, пользовательские сценарии и общие контракты проверки ответа.
