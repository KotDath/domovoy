# Domovoy

Personal AI assistant built with Flutter.

## Linux development

The application stores an optional DeepSeek API-key override with Secret
Service. Install the `libsecret` runtime and development packages before
building the Linux desktop app. On Debian and Ubuntu:

```sh
sudo apt install libsecret-1-0 libsecret-1-dev
```

At runtime, Domovoy first uses the API key saved in its settings and otherwise
falls back to the `DEEPSEEK_API_KEY` process environment variable.

## День 5 — сравнение моделей на генерации кода

В эксперименте один и тот же запрос был отправлен трём моделям: локальной
`qwen3.5:2b` через Ollama, `deepseek-v4-flash` и `deepseek-v4-pro`. Требовалось
написать самодостаточную реализацию Entity-Component-System на Dart без внешних
пакетов: с sparse/dense-отображением, жизненным циклом сущностей, component
storage, query, swap-remove, инвариантами и оценками сложности.

Автоматическая проверка в интерфейсе является только структурно-лексической:
она ищет Dart-блок и упоминания обязательных элементов. Наличие галочек не
означает, что код компилируется, правильно поддерживает инварианты или имеет
заявленную асимптотическую сложность. Поэтому ответы дополнительно были
проверены вручную как программные реализации.

### Qwen 3.5 2B

Локальная модель не справилась с задачей. Ответ содержит правдоподобные слова
про sparse set и ECS, но фактически представляет собой синтаксически неверную
галлюцинацию:

- подключены запрещённые и, вероятно, несуществующие внешние пакеты
  `sparseset` и `sparedictionary`;
- используются вымышленные конструкции и API: `set.lors`, `cctor`,
  `sparse_set_of_ints` и другие;
- классы `Entity`, `Component` и функции `main` объявляются несколько раз;
- встречается недопустимый для Dart синтаксис, а рабочие операции ECS не
  реализованы;
- query, component storage и оценки сложности присутствуют преимущественно в
  комментариях, а не в исполняемом коде;
- swap-remove отсутствует даже по структурной эвристике интерфейса.

Такой ответ нельзя довести до рабочего состояния локальными исправлениями —
реализацию необходимо написать заново. Этот прогон также показывает, что
небольшая модель может воспроизводить терминологию задачи, не удерживая её
семантику и синтаксис языка.

Метрики запуска:

| Показатель | Значение |
|---|---:|
| Prompt tokens | 146 |
| Completion tokens | 3142 |
| Всего токенов | 3288 |
| TTFT | 366 мс |
| Полная длительность | 38 979 мс |
| Оценка стоимости API | $0 — локальный запуск |
| Ресурсная оценка | 2B / 2.7 GB; CPU, RAM и энергия не измерялись |

Нулевая цена здесь означает отсутствие платы провайдеру, а не отсутствие
стоимости вычислений: локальный запуск использует процессор, оперативную память
и электроэнергию компьютера.

### DeepSeek V4 Flash

Flash сформировал гораздо более реалистичную архитектуру: отдельные
`SparseSet`, `ComponentStorage`, реестр хранилищ, поколения сущностей и несколько
вариантов query. Описание инвариантов выглядит убедительно, но код не является
рабочим.

Основные проблемы:

- конструктор `ComponentNotFoundException` ошибочно назван
  `ComponentAlreadyExistsException`, поэтому пример не компилируется;
- `SparseSet.remove()` объявлен как `void`, хотя `ComponentStorage.remove()`
  пытается вернуть его результат как `bool`;
- пример повторно вызывает `addComponent<Position>`, но реализация запрещает
  замену существующего компонента и выбросит исключение;
- уничтожение сущности использует `_aliveEntities.indexOf()`, поэтому заявленная
  сложность `O(1)` фактически становится `O(n)`;
- проверка жизни сущности использует линейный `_garbage.contains()`;
- повторный `destroyEntity()` способен повторно поместить ID в free list и
  повредить счётчик живых сущностей;
- `clear()` не очищает component storage, из-за чего переиспользованный ID может
  столкнуться со старым компонентом;
- значения компонентов индексируются непосредственно по `entityId`, а не идут
  параллельно dense-массиву. Это сохраняет быстрый доступ, но не является
  компактным dense component storage, описанным в ответе;
- уничтожение проходит по всем зарегистрированным хранилищам компонентов, а не
  выполняется за безусловное `O(1)`.

Сильной стороной ответа является идея generation-based идентификаторов: она
может защитить от использования устаревших ссылок после повторного применения
ID. Однако ошибки реализации не позволяют получить эту гарантию полностью.

Метрики запуска:

| Показатель | Значение |
|---|---:|
| Prompt tokens | 154 |
| Cache hit / miss | 128 / 26 |
| Completion tokens | 4770 |
| Всего токенов | 4924 |
| TTFT | 992 мс |
| Полная длительность | 27 930 мс |
| Оценка стоимости | $0.001340 |

Несмотря на наибольшее число completion-токенов, Flash завершил запрос быстрее
остальных моделей. Из трёх вариантов это лучший результат по сочетанию времени
и стоимости, но не готовая библиотека.

### DeepSeek V4 Pro

Pro предложил наиболее близкую к классической sparse-set архитектуру хранения
компонентов. Массив компонентов задуман параллельным dense-массиву сущностей, а
при удалении последний компонент переносится на освободившуюся позицию. Это
лучше соответствует требуемому swap-remove, чем storage в ответе Flash.

Тем не менее пример также не запускается и содержит несколько критических
дефектов:

- строка `print('Компоненты добавлены.);` не закрыта, поэтому код не
  компилируется;
- увеличение `List<int>` через присваивание `_sparse.length = entityId + 1`
  пытается создать непроинициализированные элементы и завершается ошибкой при
  включённой null safety; список нужно расширять значениями `-1`;
- `getComponent`, `removeComponent` и `hasComponent` обращаются к
  `_componentStorages[Type]` вместо `_componentStorages[T]`, поэтому добавленные
  компоненты невозможно корректно получить через generic API;
- `addComponent` не проверяет, существует ли переданная сущность;
- переиспользование ID выполнено без поколений, поэтому старый объект `Entity`
  после повторной выдачи ID начинает указывать на новую сущность;
- `SparseSet.contains()` не проверяет основной защитный инвариант
  `dense[sparse[id]] == id` и не обрабатывает отрицательные ID;
- уничтожение сущности проходит по всем хранилищам, поэтому сложность зависит от
  числа зарегистрированных типов компонентов;
- для произвольного количества типов query имеет сложность порядка
  `O(k × n_min)`, а не просто `O(n_min)`.

Pro лучше остальных передал устройство плотного component storage, но высокая
детализация и уверенное заключение «готово к использованию» скрывают тот факт,
что код не прошёл бы даже первый запуск.

Метрики запуска:

| Prompt tokens | 154 |
| Cache hit / miss | 128 / 26 |
| Completion tokens | 4386 |
| Всего токенов | 4540 |

1.8 раза дольше и по расчётному тарифу стоил примерно в 2.9 раза дороже.

### Сводное сравнение

| Модель | Корректность | Архитектурная полнота | Время | Стоимость | Практический итог |
|---|---|---|---:|---:|---|
| Qwen 3.5 2B | Критически низкая | Термины без реализации | 38.979 с | $0 API | Непригоден даже как основа |
| DeepSeek V4 Flash | Низкая без исправлений | Развитый API и поколения, но неверный storage и lifecycle | 27.930 с | $0.001340 | Лучший по скорости/цене, требует серьёзной доработки |
| DeepSeek V4 Pro | Низкая без исправлений | Лучший dense storage, но сломаны базовые операции | 50.647 с | $0.003828 | Лучший архитектурный черновик, не рабочий код |

Во всех трёх ответах причина завершения — `stop`. Интерфейс обнаружил Dart-код,
sparse/dense, `O(1)`, component storage и query во всех ответах, кроме
swap-remove у Qwen. Ручная проверка показала, почему эти признаки нельзя считать
оценкой качества: два ответа DeepSeek выглядят законченными, но не компилируются,
а ответ Qwen содержит нужные слова без реальной реализации.

### Вывод

Эксперимент показал заметный рост способности удерживать сложную программную
задачу от локальной модели Qwen 3.5 2B к DeepSeek V4 Flash и Pro. Qwen не смог
сформировать осмысленный Dart-код. Обе модели DeepSeek создали правдоподобные и
структурированные проекты, однако ни одна не выполнила ключевое требование о
рабочем самодостаточном примере.

По качеству базовой sparse/dense-идеи условным победителем является DeepSeek V4
Pro. По времени и стоимости заметно выгоднее DeepSeek V4 Flash. Выбор модели
поэтому зависит не только от её уровня, но и от требуемой задержки и бюджета.
При этом более дорогая модель не гарантировала корректный код: Pro оказался
медленнее и дороже Flash, но всё равно допустил ошибки компиляции и жизненного
цикла сущностей.

Главный практический вывод — ответы LLM нельзя оценивать по объёму, уверенности
или наличию правильных терминов. Сгенерированный код необходимо как минимум
пропустить через `dart analyze`, а затем проверить тестами: удаление среднего
элемента через swap-remove, повторное использование ID, устаревшие entity
handles, двойное уничтожение, очистку мира, замену компонентов и query после
изменений. Модель ускоряет подготовку архитектурного черновика, но компилятор,
тесты и инженерная проверка остаются обязательными.

Стоимость DeepSeek приведена как оценка по тарифу на 2026-09-07. Реальный биллинг
может отличаться из-за изменения цен, округления и правил учёта кэшированных
токенов. Локальная модель не имеет API-тарифа, но её аппаратные расходы в этом
эксперименте не измерялись.
