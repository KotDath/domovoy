# Правила репозитория

## Проект

Domovoy — персональный ИИ-ассистент в виде Flutter-приложения. Имя Dart-пакета
— `domovoy`, префикс нативного идентификатора приложения — `ru.kotdath`.

## Работа с OpenSpec

- Используйте OpenSpec-скиллы из `.opencode/skills/` для нетривиальных функций
  и изменений поведения.
- Начинайте новую запланированную работу с `$openspec-propose`, реализуйте её с
  `$openspec-apply-change`, а перед архивацией проверяйте результат с
  `$openspec-verify-change`.
- Ограничивайте каждое предложение и набор задач одним независимо проверяемым
  изменением.
- Изменения только в инструментах, агентах и конфигурации репозитория не требуют
  OpenSpec change, если пользователь явно не попросил обратного.

## Командный процесс

- Интерактивные роли команды: `architect`, `coder` и `reviewer`. Это primary-
  агенты, предназначенные для работы в отдельных сессиях.
- Для запланированной продуктовой работы источником истины служат актуальная
  инструкция пользователя и активный OpenSpec change. Существенные решения
  должны быть записаны в соответствующий OpenSpec-артефакт, а не оставаться
  только в истории терминала.
- Архитектор отвечает за требования, спецификации, дизайн и декомпозицию задач.
  Он не реализует код приложения и тесты.
- Архитектор использует штатный tool `task` с built-in subagent `explore` только
  для ограниченного read-only исследования. Выводы subagent перепроверяются
  архитектором. Task-subagent не реализует код приложения и тесты, не меняет
  OpenSpec и не заменяет независимые primary-сессии `coder` и `reviewer`.
- Кодер отвечает за реализацию, тесты и выполнение задач. Он не меняет
  требования или архитектуру без явного решения пользователя или архитектора.
- Ревьювер работает только на чтение. Он сообщает о найденных проблемах и
  никогда не исправляет проверяемый код самостоятельно.
- В общем worktree один файл одновременно может изменять только один агент.
  Перед изменением активного плана приостановите затронутую реализацию.

## Координация команды

- Используйте скилл `team-orchestration` для постановки задач, межролевых
  вопросов, решений, findings, результатов, ожидания и сообщений о блокировках.
- Штатный `task`/`explore` используйте для ограниченного read-only исследования;
  Herdr — для независимых primary-ролей и межролевых сообщений. Не создавайте
  сессии Herdr или Orca только для explore, если `task` доступен и пользователь
  не запросил иной транспорт.
- Имя агента в Herdr является транспортным адресом и не выбирает роль OpenCode.
  При запуске primary-роли передавайте роль одновременно как имя Herdr и как
  аргумент OpenCode `--agent <role>`. До отправки TASK проверяйте оба значения.
- Использование Herdr CLI из уже запущенной primary-сессии для отправки
  межролевого сообщения не считается созданием дополнительной сессии и не
  должно блокироваться.
- Когда транспорт требует указать целевого агента, используйте стабильные живые
  имена ролей `architect`, `coder` и `reviewer`.
- Каждое межролевое сообщение должно содержать тип, OpenSpec change или задачу,
  отправителя, получателя, контекст, доказательства, текст сообщения и ожидаемый
  ответ.
- Поддерживаемые типы сообщений: `TASK`, `QUESTION`, `DECISION`, `FINDING`,
  `RESULT` и `BLOCKED`.
- Не утверждайте, что сообщение доставлено, если среда оркестрации или целевая
  роль недоступна.

## Ревью и завершение

- В handoff кодер перечисляет выполненные задачи, изменённые файлы, тесты,
  запущенные команды и их результаты, отклонения, блокировки и открытые вопросы.
- Ревьювер сначала сверяет реализацию с proposal, specs, design и tasks, затем
  проводит общее ревью корректности, регрессий, архитектуры, обработки ошибок,
  совместимости платформ и покрытия тестами.
- Каждый finding должен содержать severity, категорию, файл и строку, когда это
  применимо, влияние проблемы и требуемое изменение.
- Возможные вердикты: `APPROVED`, `APPROVED_WITH_NOTES`, `CHANGES_REQUIRED` и
  `BLOCKED_BY_SPEC`.
- Не называйте работу полностью проверенной, если обязательная проверка не была
  запущена или завершилась ошибкой. Явно указывайте точное ограничение.

## Проверки Flutter

- Форматируйте Dart-код командой `dart format .`.
- Перед завершением реализации запускайте `flutter analyze` и `flutter test`.
- Сохраняйте соответствие платформенного кода идентификатору приложения
  `ru.kotdath.domovoy`.
