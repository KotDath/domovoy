# Правила репозитория

## Проект

Domovoy — персональный ИИ-ассистент в виде Flutter-приложения. Имя Dart-пакета
— `domovoy`, префикс нативного идентификатора приложения — `ru.kotdath`.

## Работа с OpenSpec

- Используйте OpenSpec-скиллы из `.opencode/skills/` для нетривиальных функций
  и изменений поведения.
- Начинайте новую запланированную работу с `$openspec-propose`, реализуйте её с
  `$openspec-apply-change`, а перед архивацией проверяйте результат с
  `$openspec-verify-change`.
- Ограничивайте каждое предложение и набор задач одним независимо проверяемым
  изменением.
- Изменения только в инструментах, агентах и конфигурации репозитория не требуют
  OpenSpec change, если пользователь явно не попросил обратного.

## Командный процесс

- `orchestrator` — единственная primary-роль команды. Он только назначает задачи,
  передаёт контекст и маршрутизирует ответы; он не исследует код, не планирует,
  не реализует и не проводит ревью самостоятельно.
- `architect`, `coder`, `coder-strong`, `coder-fast`, `verifier`, `reviewer`,
  `reviewer-light` и `explore` — subagent-роли. Оркестратор вызывает их штатным
  tool `task`; роли не вызывают друг друга напрямую.
- Для запланированной продуктовой работы источником истины служат актуальная
  инструкция пользователя и активный OpenSpec change. Существенные решения
  должны быть записаны в соответствующий OpenSpec-артефакт, а не оставаться
  только в истории терминала.
- Архитектор отвечает за требования, спецификации, дизайн и декомпозицию задач.
  Он не реализует код приложения и тесты и возвращает результат оркестратору.
- Кодер отвечает за реализацию, тесты и выполнение задач. Он не меняет
  требования или архитектуру без записанного решения и возвращает handoff
  оркестратору.
- `coder-fast` используется только для локального T0 scope; обычный `coder` —
  для T1; `coder-strong` — для T2 после contract review.
- `verifier` запускает детерминированные проверки и не выдаёт approval.
- `reviewer-light` проверяет T0/T1; `reviewer` выполняет тяжёлый T2
  contract/code review. Оба работают только на чтение, сообщают findings и
  никогда не исправляют проверяемый код самостоятельно.
- `explore` выполняет только ограниченное read-only исследование. Его выводы
  являются наблюдениями и должны перепроверяться профильной ролью до решения.
- В общем worktree один файл одновременно может изменять только один агент.
  Перед изменением активного плана приостановите затронутую реализацию.

## Координация команды

- Используйте скилл `team-orchestration` для постановки задач, межролевых
  вопросов, решений, findings, результатов, ожидания и сообщений о блокировках.
- Единственный транспорт делегирования и межролевой коммуникации — штатный tool
  `task`. Внешние терминальные мультиплексоры и отдельные primary-сессии для
  командного процесса не используйте.
- Перед назначением создавайте route card по `.opencode/policies/routing.md`.
  Tier можно только повысить. Маршруты:

  ```text
  T0: coder-fast -> verifier -> reviewer-light
  T1: architect -> coder -> verifier -> reviewer-light
  T2: architect -> reviewer(contract) -> coder-strong -> verifier -> reviewer(code)
  ```

- Оркестратор вызывает роли по точному `subagent_type`. Для продолжения работы
  той же роли сохраняйте соответствующий `task_id`. После архитектурного
  изменения или двух fix-циклов создавайте свежий контекст с коротким handoff.
- Каждое задание должно содержать тип, change или область работы, отправителя,
  получателя, контекст, доказательства, сообщение, ограничения, критерии
  приёмки и ожидаемый ответ, а также `scope_id`, `attempt_id`, tier,
  immutable `base_revision`, `contract_revision`, included/excluded scope и
  expected paths.
- Поддерживаемые типы сообщений: `TASK`, `QUESTION`, `DECISION`, `FINDING`,
  `RESULT`, `BLOCKED` и `ESCALATION`.
- Subagent возвращает сообщение оркестратору. Оркестратор передаёт его следующей
  роли новым вызовом `task` или продолжает существующий сеанс по `task_id`.
- Не запускайте параллельно задачи, способные менять одни и те же файлы.
  Реализация, изменение её плана и ревью выполняются последовательно.
- Если вызов `task` не завершился или роль вернула `BLOCKED`, не утверждайте, что
  работа или доставка результата завершена.

## Ревью и завершение

- В handoff кодер перечисляет выполненные задачи, изменённые файлы, тесты,
  запущенные команды и их результаты, отклонения, блокировки и открытые вопросы.
- Ревьювер сначала сверяет реализацию с proposal, specs, design и tasks, затем
  проводит общее ревью корректности, регрессий, архитектуры, обработки ошибок,
  совместимости платформ и покрытия тестами.
- Каждый finding должен содержать severity, категорию, файл и строку, когда это
  применимо, влияние проблемы, требуемое изменение и стабильные `finding_id` и
  `invariant_id`. Кодер ставит только `fixed_pending_review`; finding закрывает
  reviewer.
- Возможные вердикты: `APPROVED`, `APPROVED_WITH_NOTES`, `CHANGES_REQUIRED` и
  `BLOCKED_BY_SPEC`; light reviewer также может вернуть `ESCALATED`.
- Повтор одного invariant после двух исправлений возвращается architect. Два
  цикла без нового evidence дают `NO_PROGRESS`.
- Различайте `implemented`, `CHECKS_PASS` и `accepted`. Approval действителен
  только для точных `scope_id`, `base_revision`, `contract_revision`,
  `implementation_revision` и `check_result_id`.
- Не называйте работу полностью проверенной, если обязательная проверка не была
  запущена или завершилась ошибкой. Явно указывайте точное ограничение.

## Разрешения команд

- Частые repo-local команды writer-ролей (`openspec`, чтение файлов, Python 3,
  Flutter/Dart и runner) должны выполняться без повторных approval prompts.
  Для обычного локального Git используйте `.opencode/bin/repo-git`: он
  разрешает inspect-команды, `add`, обычный `commit` и другие явно
  allowlisted локальные операции. Опции не сокращаются, а пути передаются
  только после `--`, например `repo-git add -- AGENTS.md`. Wrapper
  запрещает lazy fetch и не принимает внешние config/file inputs. Прямой `git` остаётся
  `ask`, чтобы network, lossy,
  external-scope, config/alias и неподдержанные команды требовали отдельного
  решения.
- Встроенные bash-patterns не гарантируют cwd-scope. Поэтому прямой `rm` не
  разрешайте безусловно: для удаления явных путей внутри текущего Git worktree
  используйте `.opencode/bin/repo-rm`; он запрещён read-only ролям.
- Внешние сетевые Git-операции, потенциально теряющие изменения команды и
  системные команды остаются `ask`/`deny`. Доступ за пределы worktree остаётся
  `ask`.
- `explore`, `reviewer-light` и `reviewer` читают через встроенные
  `read`/`glob`/`grep` и не получают произвольный Python, файловый shell или
  Flutter/test execution. Для Git используйте
  `.opencode/bin/repo-git --read-only`, для OpenSpec —
  `.opencode/bin/repo-openspec`, для JSON, YAML frontmatter, JSON Schema и
  Python syntax — `.opencode/bin/read-check`.
  Формальные Flutter/test checks для review запускает `verifier`.

## Проверки Flutter

- Форматируйте Dart-код командой `dart format .`.
- Перед завершением реализации запускайте `flutter analyze` и `flutter test`.
- Сохраняйте соответствие платформенного кода идентификатору приложения
  `ru.kotdath.domovoy`.
