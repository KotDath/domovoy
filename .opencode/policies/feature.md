# Реализация фичи

Этот сценарий адаптирует business-feature: исследование → план/критерии →
реализация → проверка → результат. Это инструкция координатору, не исполняемый
JS-движок. Риск и evidence определены в routing.md; транспорт — team-orchestration.

## Выбрать ближайший результат

1. Используйте названный пользователем change, иначе актуальный из контекста.
   Если состояние неизвестно, поручите explore один запрос: активные changes,
   прогресс, обязательные пользовательские gates, готовые материалы и HEAD.
   При нескольких подходящих changes спросите выбор; не выбирайте старый по памяти.
   Если активного change нет, поручите architect подготовить новый по запросу;
   не возобновляйте архивированный change автоматически.
2. Сохраняйте единый change. Выберите из его tasks связанный проверяемый участок:
   что пользователь сможет делать после него. Укажите номера задач, AC, пути,
   зависимости и явные non-goals. Не объявляйте всю фичу готовой по одному участку.
3. Уже готовые исследования, спецификации и verdict переиспользуйте. Не создавайте
   новый proposal, повторный консилиум или отдельный change ради этапа.
4. Если пользователь потребовал утвердить дизайн до реализации, сначала покажите
   существующие макеты. При их отсутствии поручите architect подготовить макеты
   и описание визуальных решений. Состояние ready_for_user означает «готово к
   обсуждению», не технический approval. Findings будущего runtime/storage не
   блокируют показ. До явного одобрения зависимую реализацию не запускайте.
   Подтверждение запишите в существующие артефакты, без нового полного review
   только из-за записи решения. Не создавайте approval gate, если его не было.

## Уточнить только недостающее

По умолчанию нет обязательного research-консилиума. Если неизвестны нужные файлы
или механизм — одно ограниченное explore-задание с конкретными вопросами.
Architect нужен, когда не хватает требования, плана или архитектурного решения;
иначе передайте coder существующий план. Для нового change architect использует
openspec-propose. Для существующего — дополняет только релевантные артефакты.
Plan и Spec объединены в короткий handoff: результат, tasks/AC, решения, пути,
проверки. На планировании предложите light/heavy с обоснованием сложности;
при согласовании спеки зафиксируйте выбор пользователя. Применяйте routing.md;
T2 сам по себе не добавляет contract review или code review в heavy.

## Реализовать

Назначьте coder (light) или oneshotter (heavy) по выбранной схеме. Передайте весь
необходимый handoff, пользовательские ограничения и оставшиеся findings.
Один пишущий агент за раз; не делите Flutter UI/state/composition между
параллельными writers. Независимое read-only исследование может идти параллельно.
Coder доводит назначенные задачи вместе с тестами до рабочего состояния,
сам исправляет обычные ошибки компиляции и тестов. Не расширяет продуктовый scope.
После двух безуспешных попыток исправления одного сбоя возвращает его с evidence.
Нет нужды возвращаться к architect из-за каждой технической детали.

## Проверить и принять участок

До назначения выберите владельца каждой проверки. Coder обычно форматирует и
запускает целевые тесты, а полный Flutter-набор выполняется один раз на готовом
участке coder или verifier. Надёжные результаты на той же реализации используйте
повторно по routing.md. Если обязательных проверок не хватает, назначьте verifier
или coder с точными недостающими командами, не полный прогон по привычке.

После завершения writer передайте неизменяемую версию на проверку:
light — reviewer Sol и verifier DeepSeek параллельно; heavy — только verifier
DeepSeek. Verifier в отдельном контексте проверяет AC и формальные критерии,
reviewer ищет дефекты diff без дублирования его работы. Оба могут читать код.
Сначала дождитесь всех назначенных результатов, затем объедините findings и
поручите исполнителю исправления. Не изменяйте snapshot во время проверок.
Повторно запускайте только затронутые проверки/закрытие findings; изменение кода
в light требует актуального code verdict, даже если исходное ревью уже прошло.
Нет нового общего аудита. Исходная проверка + максимум два цикла исправлений
и целевой перепроверки; счётчик общий, смена модели/revision его не сбрасывает.
Если после второго цикла блокер остался — blocked с причиной. Подробные условия
accepted для обеих схем — routing.md. В heavy Sol-review не является условием.

При выполненных AC, обязательных проверках и отсутствии обязательных findings
покажите результат и примите участок. Без «ревью завершения» и отдельного агента
для отчёта. Продолжайте следующий разрешённый участок без нового подтверждения.
Перед завершением всей фичи проверьте взаимодействие частей; полный Flutter-набор
нужен для итогового дерева, если на нём ещё нет действующего результата.
Архивация, push и deployment не входят автоматически в /feature.

## Состояние и возобновление

Координатор держит короткую карточку в handoff; writer обновляет её в конце своего
уже назначенного этапа в `.opencode/workflow/feature-state/<change>.md`. Отдельное
назначение ради записи не нужно. При первом writer-вызове включите этот точный
путь в scope. Architect имеет разрешение писать только эти process-файлы и OpenSpec.
Файл состояния не заменяет OpenSpec tasks или доказательства проверок.

Карточка содержит change, результат участка, scope_id, stage, tasks/AC, tier,
пользовательские gates, base SHA, стартовый diff (включая чужие правки), пути,
решения, recommended_mode/execution_mode/rationale/selection_source, task_id ролей,
evidence, открытые findings и rework_count (0..2).
Stages light: ready → implementing → checking+reviewing → accepted;
heavy: ready → implementing → checking → accepted; дополнительно
ready_for_user, blocked. Contract review отмечается как подготовка текущего участка.
После compaction сверяйте карточку с актуальными файлами и пользовательским
решением; не повторяйте весь pipeline. Если состояние или evidence нельзя
подтвердить, восстановите только недостающую информацию, не считайте её PASS.

## Примеры маршрутов

- Готовая согласованная light: coder → параллельно reviewer + verifier → результат.
- Согласованная heavy: oneshotter → verifier → результат без Sol-review.
- Макеты готовы, approval pending: показать → ждать решения; не runtime audit.
- Finding: назначенный исполнитель исправляет → автор finding перепроверяет.
- После двух циклов блокер остался: blocked, не новая модель для обнуления лимита.
- Уже есть актуальный flutter test: verifier использует evidence и проверяет AC,
  не запускает тот же тест повторно без причины.
